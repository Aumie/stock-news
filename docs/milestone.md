On the Stats page itself, the old three-figure ingestion-lag block (avg/p50/p95 — unused, per the user: "i dont need ingest lag 3 stats") was deleted outright, replaced by one "total ingestion in the past Nd" number and a `7d | 30d` toggle that also scales the rolling-volume chart's own averaging window (a real 30-day rolling average in 30d mode, not a 7-day average stretched over more points) and the price-deltas range — one shared window for the whole per-symbol section. `GET /stats` gained `?days=7|30`; a real bug was caught while wiring it — `Literal[7, 30]` on a query parameter rejects the literal string `"30"` in this pydantic version even though `30` is listed as valid, fixed by typing it as a plain `int` with an explicit `in (7, 30)` check instead. **Live-verified the window boundary is a real filter, not a no-op**: inserted a synthetic 25-day-old row directly into `daily_symbol_features` and confirmed `?days=7` excluded it while `?days=30` included it (`15` vs `1014` articles) — the two windows had returned identical results on the first live check purely because the real account's data didn't yet span 30 days, so this synthetic check was needed before trusting the fix.

**The 7d/30d toggle was then corrected to be per-symbol** — the user caught it immediately after the single page-wide toggle version shipped ("7d 30d should be per symbol"). `GET /stats` was redesigned to return `window_7d`/`window_30d` for every symbol in one response (no query param at all), so each symbol's toggle switches instantly with no refetch; the user also asked directly whether this doubles query load at scale ("what if we have 100 symbols"), resolved by fetching only the 30-day window per symbol and deriving the 7-day figures from that same query (two rolling-average window functions, one `FILTER`-based conditional sum, and a Python-side list slice) — 3 queries per symbol total, not 6, regardless of window count.

**News backfill on watchlist-add widened from 14 to 30 days to match the price side, then hit and fixed a real third-party reliability problem**: the user's follow-up question ("and when first add symbol it pull last 30d news right?") surfaced that news backfill hadn't actually moved to 30 days yet. Widening it immediately exposed that Finnhub's `company-news` endpoint doesn't reliably serve a single 30-day request for a busy symbol — live-tested against INTC: 9.3s at 14 days, but timed out entirely (47-98s) at 20/25/30 days. Fixed with chunked fetching (`FETCH_CHUNK_DAYS=14`, 2-3 sequential calls per 30-day backfill instead of one wide call) — but live-testing *that* fix surfaced a second, deeper problem: the same endpoint's response time for the same symbol was wildly inconsistent from call to call, with 4 consecutive identical requests all timing out moments after one had succeeded in 2s. This ruled out chunk width as the real fix and pointed to genuine API-side unreliability under repeated calls. **Resolved with the user's chosen option among three presented**: each chunk's fetch is now best-effort — a timed-out or failed chunk logs a warning and is skipped rather than failing the whole `POST /watchlist` request. **Live-verified while Finnhub was still in its actually-degraded state**: added INTC for real, 2 of 3 chunks genuinely timed out and were logged as warnings, and the request still completed with a real `201` — 17 real articles landed from the one chunk that succeeded, real price data landed independently from the unaffected Yahoo-based trigger, and the watchlist add itself never failed.

**Real bug reported directly by the user, found the same session**: "when i swap tab to watchlist add goog and back to livefeed i dont see goog news." Root cause: the best-effort fix above initially recorded backfill progress unconditionally, even when every chunk failed — so GOOG's first add (every chunk failed against Finnhub) still got marked "backfilled," and after being removed and re-added, `backfill_on_add`'s no-op check saw that stale progress row and silently skipped fetching entirely, leaving GOOG on the watchlist with zero articles and no error anywhere. Fixed: progress is now only recorded once at least one chunk genuinely reaches Finnhub (zero real articles from a reachable chunk is a legitimate outcome; zero chunks reached at all is not "backfilled"). **Live-verified against the real stranded data**: cleared GOOG's bad progress row, re-triggered the backfill for real, and confirmed 24 real GOOG articles landed and now appear in `GET /feed` — the exact reported symptom, fixed.

**Watchlist-add and "load older news" moved off the request path onto a Celery + RabbitMQ background job queue, per direct user request**: "when add symbol shouldnt it be instant, add leave loading news as background job?" — the best-effort chunk fixes above made backfill failures non-fatal, but the request could still block for a long time waiting on Finnhub. User specifically asked for a durable (Hangfire-style) job system rather than FastAPI's in-process `BackgroundTasks`; chose RabbitMQ as Celery's broker after working through the real alternatives — self-hosting on Cloud Run doesn't actually solve durability (no real persistent disk there) and still costs like an always-on VM, while CloudAMQP's free "Little Lemur" shared plan (verified live to genuinely exist, not a trial) gives a real managed broker with zero hosting burden. `POST /watchlist` now returns as soon as symbol validation and the DB write finish; the actual news + price backfill runs in a new `celery-worker` container. Hit and fixed two real, non-obvious RabbitMQ 4.x/Celery incompatibilities along the way (both confirmed live, not found in docs first): the default task queue declaration and Celery's own `mingle`/`gossip` startup bootsteps both rely on a queue pattern RabbitMQ 4.x has deprecated and rejects outright — fixed with a durable task queue plus `--without-mingle --without-gossip --without-heartbeat` (CLI-only flags, not available as settings). `POST /feed/load-older` got the identical fix once the user reported "loading older news takes so long" — traced live to three sequential ~31s Finnhub timeouts (95+ seconds for one click); now pages Postgres first and, if empty, enqueues one background backfill window per symbol and returns immediately (`backfilling: true`) instead of retrying synchronously. **Live-verified**: the same load-older call went from 95+ seconds to **0.27 seconds**, with the Celery worker confirmed picking up the enqueued task within milliseconds.
