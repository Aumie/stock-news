# Stock news digest — requirements summary

## 1. Overview

A microservices-based system that continuously ingests stock-related news for symbols users are watching, embeds it into a vector database, and lets users query or receive digests of recent news relevant to their watchlist — via a retrieval-augmented generation (RAG) pipeline.

Built as a portfolio project to demonstrate: event-driven ingestion, dynamic subscription management, ETL/ELT pipeline design for both structured and unstructured data, a lightweight feature store, vector database usage for RAG, data quality practices, cloud deployment, automated testing, and CI/CD with infrastructure as code.

Each service is internally built with **Domain-Driven Design and Test-Driven Development; Clean Architecture's layering applies to the Python services specifically, not the Go ones** — see §8's "Architecture pattern" entry for what that means concretely in this codebase.

This document is split into **v1** (the sections below, excluding §12) and **v2** (§12, "Phase 2 — Future extensions"). v1 is a complete, coherent, shippable portfolio piece on its own — pure news RAG plus a basic price/feature-store side for stats. v2 adds sentiment scoring, chat-queryable structured/pattern data via LLM tool-calling, and technical pattern detection. Everything in v2 was fully designed already; it's deferred, not abandoned — see §12 for the full detail, preserved rather than deleted.

## 2. Goals

- Show a real incremental/streaming ingestion pipeline, not a one-time batch load
- Demonstrate microservices separation with clear single responsibilities
- Support per-user watchlists with efficient, non-duplicated data collection
- Provide a working RAG query interface (ask questions, get digests) over ingested news
- Keep v1 scope achievable solo, with free-tier services — **"a few weeks" honestly describes milestones 1–4 (§9's MVP checkpoint: core RAG loop, auth, dynamic coverage, microservices split), not the full 1–9 stack**. Milestones 5–9 add a second full pipeline (structured data + dbt), a UI, cloud migration, and CI/CD/Terraform — real work, realistically more like 6–8 weeks of solid solo evenings/weekends on top of the MVP, not padding but not "a few weeks" either. Stated explicitly here rather than left as an implied footnote at milestone 4

## 3. Users & authentication

- Single user type (no admin/roles needed)
- Login via **Google OAuth2 only** — no password-based auth
- On first login, create a user record keyed on Google's stable subject ID (`sub`)
- **Concrete flow, given the UI is Streamlit (§6)**: the UI service handles the actual Google OAuth handshake itself via Streamlit's native `st.login()`/`st.user` (confirmed built-in since Streamlit 1.42 — no manual redirect/callback handling needed on the UI side). Once `st.login()` returns a verified Google identity, the UI calls Auth service with that verified `sub`, which creates/looks up the user record and issues the app's own signed JWT — Auth service's OAuth-callback role is invoked *from* the UI after Google verification succeeds, not the direct target of Google's redirect itself. The returned JWT is stored in `st.session_state` for the browser session and attached to every Query API call (watchlist management, chat queries) as an Authorization header
- Session handled via signed JWT issued by the backend after OAuth callback — **explicitly specified, not silently left unstated**: short expiry (24h), re-login via Google after expiry in v1 (acceptable given the single-user-type, low-friction nature of this app); logout is client-side token discard only (`st.logout()` clears `st.session_state`) — there's no server-side revocation/blocklist in v1, so a JWT remains technically valid until it expires even after "logout." Worth a real fix if this app ever handled anything sensitive; acceptable for a portfolio project's threat model
- **Refresh-token flow deferred to Phase 2 (§12.0)** — v1 deliberately accepts "re-login every 24h" rather than building refresh/rotation logic, to keep the auth surface small; this is a real, bounded piece of future work, not an oversight
- Auth events (login success/failure) are logged — see §5's logging note

## 4. Functional requirements

### 4.1 Watchlist management
- Authenticated users can add/remove stock symbols to their personal watchlist
- A symbol can be watched by multiple users simultaneously
- Symbols are validated against a known ticker reference (e.g. Finnhub's symbol lookup) at add-time, before being persisted — invalid/unrecognized tickers are rejected with an error, so the poller never burns API calls on garbage input
- **Known gap**: this validates Finnhub coverage only. A symbol that passes and later lands in the Marketaux overflow bucket (§4.2) is never checked against Marketaux's own symbol coverage — if Marketaux doesn't cover it, that symbol silently gets zero overflow articles with no error surfaced. Low practical impact (major US tickers are covered by both), not fixed further in v1

### 4.2 Listening / ingestion
- The system listens only to symbols that are **actually present** in the watchlist table (no blanket listening to all possible symbols)
- One logical poll per unique symbol per cycle, shared across all users watching it — not one poll per user
- A single **poller**, re-reading the distinct set of watched symbols (`SELECT DISTINCT symbol FROM watchlist`) at the start of every cycle — this *is* the diff, so no separate subscription-manager service or persisted subscription lifecycle is needed
- Poll cycle is **60 seconds** — this is the interval the Finnhub rate-limit math (below) is calculated against. **Mechanism, corrected for cost twice over**: (1) not a persistent "always-on" service running an internal loop — that would cost real money (verified: Cloud Run's free tier is 180,000 vCPU-seconds/month, only ~50 hours; continuous operation needs ~2.59M vCPU-seconds/month, ~14x over budget, ~$65/month in practice); (2) not a one-shot Cloud Run *Job* either, despite that being the first fix — Jobs spin up a fresh container per execution with no instance reuse, so a Job firing every minute re-fetches its secrets from Secret Manager on every single invocation (~43,200/month, over the free 10,000 access-operations/month, see §8). The actual mechanism: **Cloud Scheduler triggers the poller via HTTP against a Cloud Run *Service*** (§6) — Services reuse warm instances between requests under Cloud Run's default request-only CPU billing, so an instance triggered every 60 seconds almost certainly stays warm between triggers, costing $0 in CPU during the gaps (billed only for actual request-processing seconds) while also letting secrets fetched at that instance's original cold start stay cached in memory instead of being re-fetched every invocation
- Primary source: **Finnhub** free tier (60 calls/min, no daily cap, real-time company news) — one call per symbol per 60s cycle, capped at ~40–45 concurrently watched symbols to stay safely under the rate limit with retry/jitter headroom
- Overflow assignment rule (when watchlist exceeds the ~40–45 cap): rank symbols by distinct watcher count (most-watched first), tie-broken by earliest `added_at`; the top ~40–45 stay on Finnhub's fast lane, the rest are served by Marketaux — this prioritizes API budget toward symbols affecting the most users, and is explicit/deterministic rather than arbitrary at runtime
  - **Known gap: no hysteresis, so a symbol sitting right at the boundary could flip sources between cycles** as watcher counts fluctuate — each flip changes that symbol's effective latency and dedup source. Not fixed in v1 (watchlist churn is realistically slow enough that this rarely triggers in practice), but stated explicitly rather than left unacknowledged, same treatment as the other known gaps in this doc
- Secondary source: **Marketaux** free tier (100 calls/day, batches multiple symbols in one call) — used for (a) overflow per the rule above, and (b) cross-source redundancy to improve recall and exercise real cross-source dedup
  - Marketaux's per-request symbol limit couldn't be confirmed (their docs page blocks automated fetching, and no public source states a number) — rather than assume "one call covers everything," the overflow list is batched conservatively at **20 symbols per call**, split into multiple sequential calls if larger. This makes the design correct regardless of what the real limit turns out to be. **This is the single highest-risk unverified technical assumption in this doc — a live test call before building the overflow logic would resolve it in minutes and should happen early.**
  - **Second thing to verify in that same live check**: whether the 100/day cap resets on a rolling 24h window or a fixed clock boundary (most free-tier APIs reset at UTC midnight). §4.2's cadence formula treats the budget as smooth across the day — fine on average, but if it's a fixed-boundary reset, a burst of catch-up calls (e.g. after downtime) right before the boundary could exhaust the day's quota early and leave zero overflow coverage until it rolls over. Not a design change needed now, just a second fact to confirm alongside the symbol-limit check rather than assumed
  - Cadence scales with overflow size to stay within the 100/day budget: at ≤20 overflow symbols, one call/cycle supports the original ~14 min cadence; beyond 20, each cycle needs `ceil(overflow_count / 20)` calls, which lowers the achievable cadence proportionally (e.g. ~40 overflow symbols → 2 calls/cycle → ~28 min cadence) — this is a live trade-off, not a fixed number, and should be computed from the actual overflow count at runtime
- Both sources are REST polling only — neither offers push/webhook delivery on free tiers (that capability is gated behind paid/enterprise plans, e.g. how Benzinga's real push feed powers Webull/Bloomberg). If this ever moved to a paid tier, the poller would become a webhook receiver feeding the same downstream queue — noted here as a deliberate free-tier trade-off, not an oversight
- New articles are published to a shared message queue, tagged with symbol and timestamp

### 4.3 Processing
- Consumes articles from the queue
- **Dedup uses a single, unified priority order — not two independent mechanisms for "within-source" vs. "cross-source"**, since both are really the same question ("have I already seen this article?") and canonical URL, when available, is a strictly better identifier than either fallback for both cases:
  1. **Canonical URL, when either API exposes one** — checked first, regardless of whether this is a same-source re-poll or a different-source/different-symbol discovery. This is the most precise identifier available and naturally covers both cases in one mechanism, rather than the within-source and cross-source paths using different columns that don't reference each other
  2. **Content hash (headline + source + `published_at`, rounded to the minute — never `ingested_at`), when no URL is available** — within-source fallback only: catches the same feed item re-polled from the same source. **The timestamp choice matters and was previously left ambiguous**: `articles` has both `published_at` and `ingested_at` (§7); hashing on `ingested_at` would silently break tier 2 entirely, since a re-poll of the same article gets a fresh ingestion time every cycle, so the hash would never match twice and every re-poll would land as a new row — the exact opposite of what tier 2 exists to do, and a bug that passes a naive first-poll test since there's nothing to dedupe against yet. Must be `published_at`, rounded to the minute to absorb any source-side jitter in how the same article's timestamp gets reported across polls, without the bucket being coarse enough to risk matching genuinely different articles. This cannot match across sources by construction (different source values), which is intentional, not a gap — cross-source matching is handled by tier 3
  3. **Published date (day-level) + normalized/fuzzy-matched headline, when no URL is available** — cross-source fallback only, for the case tier 1 can't cover. The match key must NOT include `source` (defeats cross-source dedup by construction — see §4.2) and must NOT include `symbol` either, since an article can legitimately be tagged under multiple symbols (§7's `article_symbols`) and keying on symbol would treat the same article polled under two different tickers as two separate articles
- When a cross-match is found at any tier, the article itself is not reprocessed (no re-chunk/re-embed) — instead, a new `article_symbols` row is added for the newly-seen symbol if that association doesn't already exist
- **Dedup is enforced at the database level for tiers 1–2, not just in application logic** — Cloud Run auto-scales the processing service by default, so two workers can genuinely race on discovering the same underlying article via two different symbol polls before either has matched it. Uniqueness constraints (§7) make the insert path atomic rather than relying on a check-then-insert race:
  - **Corrected during implementation**: this originally specified `ON CONFLICT DO NOTHING` followed by a separate fetch of the existing row on a miss — that has its own race, since a concurrent insert landing between the `DO NOTHING` and the follow-up `SELECT` can make the `SELECT` return zero rows. The actual, correct pattern is one atomic round trip: `ON CONFLICT (canonical_url) DO UPDATE SET canonical_url = EXCLUDED.canonical_url RETURNING id, (xmax = 0) AS inserted` (same for `content_hash`) — `(xmax = 0)` is Postgres's standard way to tell whether a row was just inserted or the conflict clause updated an existing one. Found and fixed during implementation (`decision_log_claude.md`), verified against real concurrent writes; corrected here so the spec itself doesn't describe the buggier version
  - `articles.content_hash` is UNIQUE, same atomic `DO UPDATE ... RETURNING` pattern — fully closes the within-source race when no URL exists
  - Tier 3 (fuzzy headline, no URL) can't be a hard constraint — fuzzy matching isn't exact equality, so a unique index can't enforce it. A rare race here could still produce two near-duplicate `articles` rows; this is an accepted, low-frequency data-quality edge case (no data loss, just an occasional duplicate a later cleanup pass could merge), not something v1 fully closes
  - **Additional gap found during implementation**: tier 3 only runs when the article *currently being processed* lacks a URL (§4.3's tier ordering, "when no URL is available") — it doesn't cover the case where *that* article has no URL but a different, already-stored candidate for the same real-world story *does* have one. Tier 1 can't match (nothing to match on), and tier 3 never triggers a URL-based comparison. Observed directly: a Finnhub article with a `canonical_url` and a Marketaux article without one, covering the same story, landed as two separate rows with no path to reconcile them. Same category as tier 3's other accepted limitations above — not fixed in v1, but wasn't previously written down until implementation surfaced it
  - `article_symbols` has a composite UNIQUE constraint (or composite primary key) on `(article_id, symbol)`, inserted via `ON CONFLICT DO NOTHING` — makes adding a symbol association idempotent regardless of concurrent or retried attempts
- Chunks article text and generates embeddings
- Writes embeddings + metadata (associated symbols via `article_symbols`, source, timestamp) to the vector database
- Logs ingestion activity (what was added, when) for lineage/auditability

### 4.4 Query / digest
- Users can ask natural-language questions about news for their watched symbols
- Users can request a digest ("what's new this week for my watchlist")
- Retrieval is filtered by the requesting user's watchlist symbols at query time (fan-out happens at query time, not ingest time)
- Retrieved chunks are passed to an LLM to generate a synthesized answer/digest
- **Guardrail**: if retrieval returns nothing relevant (empty or low-similarity results) for the question asked, the LLM must say it doesn't have news on that rather than speculating — the prompt explicitly instructs it to answer only from the retrieved chunks and to state when there's insufficient grounding, instead of filling the gap with a plausible-sounding but ungrounded answer (a real risk for financial-signal questions specifically)
- **Query API's endpoint is a streaming HTTP endpoint (FastAPI `StreamingResponse`), not a buffered JSON response** — it proxies the LLM's own `stream=True` output chunk-by-chunk rather than waiting for the full completion and returning it all at once. This is what lets the UI (§4.5) actually stream tokens end-to-end via `st.write_stream`, rather than the UI being capable of streaming while the backend silently buffers the whole answer first
- **LLM spend ceiling**: a spend limit set directly on the LLM provider account (OpenAI/Anthropic's own budget/usage-limit setting), not a custom monitoring dashboard — this is a demo project, so the simplest honest option beats building monitoring infrastructure for it. When the ceiling is hit and the provider starts rejecting calls, Query API surfaces that plainly to the user ("this demo has a spending cap and it's been reached today") rather than a generic error or a silently degraded response — same honesty principle as the empty-retrieval guardrail above, just for a different failure cause

### 4.5 UI
- **Watchlist management view**: add/remove symbols (§4.1), surfacing the Finnhub-lookup validation error inline when a symbol is rejected — this is the UI for the functional requirement everything else in the pipeline depends on, and needs its own surface rather than being assumed
- Query input with optional symbol/ticker filter
- Digest/answer display with cited sources
- Live feed showing recently ingested articles (demonstrates real-time ingestion)
- Stats view backed by the analytics queries defined in §4.6 (articles ingested today, tickers tracked, ingestion lag trend, 7-day rolling article volume per symbol)

### 4.6 Structured data & feature store
- All structured data lives in **BigQuery**, not the Postgres/pgvector host — this is where dbt operates, so keeping it in one warehouse avoids cross-database plumbing
- This is a separate batch pipeline, entirely independent of the poller service and its 60s cycle — different cadence, different failure mode, deliberately not bolted onto the continuous news loop
- `prices` is **append-only, no rolling deletion** — unlike GCS's raw-article lifecycle rule (§5), price data isn't redundant once processed and storage cost is negligible even over years
- **Scheduled run, once daily** (~16:05 ET, after US market close): a Cloud Scheduler trigger invokes a Cloud Run job that pulls the day's completed daily candle (open/high/low/close/volume) per watched symbol, finalizes that day's `prices` row, then runs the dbt transform below. **Price source corrected during milestone 5**: Finnhub's candle endpoint is no longer free-tier (live `403`, confirmed against the spec's assumed key) — Yahoo Finance's chart API (`query1.finance.yahoo.com/v8/finance/chart/{symbol}`) is used instead, verified live (no key, standard browser `User-Agent`, real OHLCV + timestamps). Stooq was tried first and rejected — it now sits behind a JS anti-bot challenge a batch job can't pass. See `decision_log.md`'s "Data & storage" section
- **dbt transform**: (dbt-core, free, no hosting cost) transforms `prices` + article/ingestion data into the **feature-store-lite table** (`daily_symbol_features`, see §7): article count, ingestion lag, and price/volume per symbol per day — one definition, multiple consumers (stats UI, potential future ML use), which is the actual point of a feature store. dbt also gives this pipeline data tests (not-null, uniqueness) and auto-generated lineage documentation for free, directly supporting the lineage-documentation requirement in §5
  - **Date grain is driven by the union of `prices` dates and article-activity dates, not gated on a `prices` row existing.** News gets ingested every day, including weekends/holidays when markets are closed and `prices` has no row — the whole point of continuous polling is catching weekend developments before Monday, so a `daily_symbol_features` row must still exist for those days. Price columns (`price_close`, `price_volume`, `price_change_pct`) are simply null on non-trading days; article columns (`article_count`, `avg_ingestion_lag_seconds`) populate normally regardless. This is a deliberate choice, not an omission — an inner join against `prices` would silently make weekend article stats invisible to the UI
- **Materialized as a dbt table (`materialized: table`), not a view**: this aggregation joins articles/article_symbols/prices and computes window functions — expensive relative to a raw read, and only needs to be as fresh as the daily batch cadence, since it's read far more often (every stats-UI load) than it changes (once/day). That combination — expensive to compute, cheap/frequent to read, tolerant of daily-level staleness — is exactly the profile materialization is for
- No Airflow: this is a small number of sequential steps, which doesn't justify a DAG orchestrator's operational weight, and a managed Airflow (Cloud Composer) has no free tier — Cloud Scheduler + a plain sequential script inside a Cloud Run job gets the same outcome for free
- The stats UI's queries are written to intentionally showcase non-trivial SQL — window functions for 7-day rolling article volume, percentile/average ingestion lag, day-over-day deltas — rather than flat `COUNT`/`GROUP BY` only

## 5. Non-functional requirements

- **Cost**: must run on free-tier services during development (news API, message queue, vector DB, hosting, storage, analytics). The only accepted paid cost is the LLM/embeddings API. Every other service is chosen specifically for a confirmed perpetual "Always Free" tier, not a time-limited trial or new-account credit — see §8 for the reasoning behind each pick, and the GCS retention note below for the one usage pattern that could otherwise creep toward a free-tier ceiling over a long-running deployment
- **Compute-billing correction (found late, took two passes to actually land, worth flagging explicitly)**: this doc originally described the poller as an "always-on service," which would have quietly broken the cost commitment above — Cloud Run's free tier (180,000 vCPU-seconds/month, ~50 hours) covers a small fraction of continuous 24/7 operation, and running one instance always-on costs roughly $65/month in practice. First fix: made the poller a Cloud Scheduler-triggered one-shot Job (§4.2, §6), mirroring the daily batch job's pattern — this solved the compute cost, but broke something else: Jobs don't reuse instances between executions, so a Job firing every minute re-fetched its secrets from Secret Manager on every invocation, ~43,200/month against the free 10,000 (§8's Secrets entry) — a real but trivial overage (~$0.10–$0.40/month), not another $65/month-sized mistake, but worth eliminating rather than quietly accepting. Second fix: the poller is a Cloud Run **Service** triggered via HTTP by Cloud Scheduler, not a Job — Services reuse warm instances between requests under the same request-only CPU billing, so it costs $0 between triggers while also letting secrets stay cached instead of being re-fetched every invocation. Processing's Pub/Sub subscription is push-based for the same original reason (pull would require the same continuous polling the poller had to avoid). The one residual, bounded (not eliminated) cost risk left in the whole doc is the UI service's WebSocket-based reactivity conflicting with scale-to-zero — mitigated with a low request timeout and a capped `max-instances`, not fully removable while keeping Streamlit's live UX (§6, §8)
- **Latency**: news should be queryable within roughly 1–2 minutes of publication for symbols served by the primary source (Finnhub), given the watchlist stays under the ~40–45 symbol safe cap (see §4.2); overflow/secondary-source symbols (Marketaux) refresh on a cadence that scales with overflow list size, ~14 minutes at ≤20 overflow symbols and coarser beyond that (see §4.2's cadence formula), due to its 100 req/day free-tier cap
- **Scalability (conceptual, not required at scale)**: architecture should not duplicate polling for symbols watched by multiple users
- **Data quality**: basic validation on ingested articles (non-empty text, valid symbol, no duplicate ingestion)
- **Storage retention**: raw articles landed in GCS are redundant once processed into embeddings — a lifecycle rule deletes them after 7–14 days so usage stays bounded regardless of how long the poller runs, rather than slowly approaching GCS's 5 GB Always Free ceiling
- **Logging**: every service logs to stdout/stderr, which Cloud Run captures into Cloud Logging automatically — no separate logging infrastructure to build. Cloud Logging's Always Free tier (50 GB ingestion/month, 30-day retention) is separate from GCP's general trial credit, consistent with every other free-tier pick in this doc. Beyond §4.3's ingestion-lineage logging (what was added, when), each service logs errors/exceptions, and Auth specifically logs login success/failure events (§3) — this is distinct from the poller-liveness gap noted in §11, which is about detecting *silent* failure (still running, producing nothing), not logging *loud* failures like exceptions
  - **Format switches by environment, not the logging calls themselves**: one set of log statements throughout the codebase (`logger.info("processed article", article_id=..., symbol=...)`), with a single formatter chosen once at process startup via an env var (`ENV=dev` vs `ENV=prod`) — using **structlog**'s `ConsoleRenderer` for local dev (readable, easy to eyeball in `docker compose logs`) and its `JSONRenderer` for Cloud Run (so Cloud Logging can auto-parse fields — severity, labels, trace context — instead of treating each line as an unstructured text blob). No duplicated logging code, no per-call-site branching, just one config decision at startup
- **Documentation**: architecture diagram, data lineage notes, and setup instructions in the README

## 6. Architecture (services)

**Built as real, separate microservices from the start — no monolith phase.** Considered building v1 as a modular monolith first and splitting later, but rejected it: §2 explicitly lists "demonstrate microservices separation" as a portfolio goal, and a huge amount of design work in this doc (per-service IAM lockdown, the Cloud Run Service-vs-Job distinction, Pub/Sub push subscriptions, the free-tier cost math computed per service) is specific to these being separate deployables — none of it would get exercised sitting inside one codebase. This doesn't add work beyond what §9's milestones already plan; it just means building each milestone's pieces as their own deployable from day one rather than collapsing them into one codebase and unwinding that later.

**Polyglot by design, not by accident** — Python where the ecosystem matters (embeddings, RAG/LLM orchestration, dbt), Go where performance/concurrency matters (identity, polling), reflecting backend breadth alongside the data-engineering core rather than diluting either:

| Service | Language | Responsibility |
|---|---|---|
| Auth service | **Go + gRPC** | JWT issuance and user record creation, called from the UI service after Streamlit's `st.login()` verifies the user with Google directly (§3) — Auth doesn't handle the OAuth redirect itself, it exchanges an already-verified Google `sub` for the app's own JWT via a gRPC/Protobuf contract (a narrow, well-defined interface, and a genuine cross-language boundary worth showcasing: Python UI calling a Go service). Small, self-contained, zero ML dependencies — a natural, common real-world fit for Go. Kept as its own service rather than folded into Query API, not because it's technically required, but because §2 explicitly lists "demonstrate microservices separation with clear single responsibilities" as a goal, and Auth is a clean, self-contained boundary to keep separate for that purpose. Contrast with the poller merge, where the subscription-manager's responsibility didn't just overlap with the poller's — it fully dissolved into a query the poller already had to run, a stronger argument than "distinct responsibility" alone provides. **Not publicly reachable** (§10.5) — only the UI service's own service account can invoke it; no reason for the public internet to reach it directly |
| Poller service | **Go** | **Cloud Run Service, triggered via HTTP by Cloud Scheduler every minute — not an always-on service with an internal loop, and not a one-shot Cloud Run Job either** (§4.2; both those framings were tried and corrected, see §5). Go fits well here too: I/O-bound concurrent HTTP polling across ~40–45 symbols is a natural goroutine/worker-pool pattern, no ML dependencies, and Go's faster cold start further de-risks the warm-instance assumption below. Default request-only CPU billing + min-instances=0, same as every other service here — the every-60-second trigger cadence means the instance almost certainly stays warm between invocations (Services reuse instances, unlike Jobs), so it costs $0 in CPU during the gaps and lets secrets stay cached across invocations. Each invocation reads distinct watched symbols from the DB (no separate subscription lifecycle), polls Finnhub (primary, news) and Marketaux (overflow/redundancy news), publishes raw articles to queue, lands them in GCS. Does not touch price data — that's the daily batch job's responsibility (below), kept separate since it runs on a completely different cadence. **Not publicly reachable** (§10.5) — only Cloud Scheduler's service account can invoke it; a public trigger endpoint would let anyone burn the carefully-budgeted Finnhub/Marketaux rate limits on demand |
| Message queue | — (infra) | Decouples ingestion from processing — GCP Pub/Sub (Always Free 10 GB messages/month — confirmed via Google Cloud's own quota docs as a permanent Always Free allowance, not trial credit; it doesn't expire, though Google notes the limit is subject to change) |
| Raw landing storage | — (infra) | GCS bucket holding raw article payloads pre-processing (Always Free 5 GB, with a 7–14 day lifecycle rule — see §5) |
| Processing service | **Python** | Consumes queue, dedupes (within- and cross-source, see §4.3), chunks, embeds, writes to vector DB, logs lineage. Stays Python: embeddings (sentence-transformers) and v2's FinBERT/TradingPatternScanner are Python-only ML dependencies — switching to an API-based embedding provider purely to unlock Go would trade a free/local cost for a paid one just to enable a language choice, not a good trade. **Pub/Sub push subscription, not pull** — Pub/Sub itself invokes Processing's HTTP endpoint per message, so the service scales to zero between messages instead of continuously polling for work (verified: pull subscriptions require a continuously-running consumer, the same always-on cost problem as the original poller framing). **Not publicly reachable** (§10.5) — only Pub/Sub's push service account can invoke it |
| Query API service | **Python** | Retrieves relevant chunks filtered by user's watchlist, calls LLM, returns answer/digest. Stays Python deliberately, even though Go could handle the HTTP/SSE streaming fine — this is the most-iterated-on piece of the whole project (especially once v2's tool-routing lands), and Python's RAG/LLM tooling ecosystem is more mature right now; not worth fighting language ergonomics on the hardest part. **Also owns watchlist management** (§4.1: add/remove/list, Finnhub-lookup validation at add-time) — the general authenticated user-facing API surface, not just query/digest; folded in here rather than a dedicated watchlist service, consistent with the poller/subscription-manager merge reasoning against over-splitting services with no independent lifecycle. **Also owns JWT verification** on every incoming request (the Authorization header attached by the UI, §3) — using the shared JWT signing secret (§8's Secret Manager entry), verified locally against the token's signature and expiry, not by calling back to Auth service per request. **Not publicly reachable** (§10.5) — only the UI service's own service account can invoke it. This matters more here than anywhere else in the table: an exposed Query API endpoint doesn't just waste cheap compute, each hit can trigger a real LLM API call — the one cost this doc has always accepted, but never meant to be attacker-controlled |
| Vector database | — (infra) | pgvector on Supabase free Postgres — doubles as the article metadata store. Preferred over Neon, though the margin is narrower than it first looks: the poller's watchlist query runs unconditionally every 60s regardless of news volume, so neither Neon's 5-min autosuspend nor Supabase's 7-day idle-pause actually fires under normal operation. The real residual difference is resilience to *poller downtime* specifically — Supabase's 7-day window absorbs an extended outage without a cold start, Neon's 5-min window doesn't (see §8) |
| Analytics / feature store | — (infra) | BigQuery table (`daily_symbol_features`, see §7 and §4.6) — serves the stats UI; Always Free up to 10 GB storage / 1 TB query per month |
| Daily batch job | **Python** | Cloud Scheduler (free tier) triggers a one-shot Cloud Run **Job** daily (evening, after market close) — pulls the day's completed OHLCV, runs the dbt transform into `daily_symbol_features`, deliberately not orchestrated by Airflow (see §4.6). Stays Python regardless of any language preference: dbt-core is a Python CLI tool, so whatever container runs `dbt run` needs a Python runtime present. A Job (not a Service, unlike the poller above) is the right fit here specifically because it only runs once a day — no per-invocation secret-refetch concern at that frequency, unlike the poller's every-minute cadence which needed the Service/warm-instance-reuse fix (§4.2, §8) instead. Two Cloud Scheduler job definitions now exist (this one + the poller's every-minute HTTP trigger) — both fit inside Cloud Scheduler's confirmed free tier of 3 job definitions per billing account |
| UI service | **Python (Streamlit)** | Serves all of §4.5 — watchlist management, chat-style query interface (`st.chat_message`/`st.chat_input`/`st.write_stream`, consuming Query API's streaming endpoint, §4.4), live ingestion feed, and stats dashboard (§4.6). Streamlit is Python-only, no language choice here. Also owns the Google OAuth handshake via `st.login()`, then calls Auth service to exchange the verified identity for the app's JWT (§3) — the only service that talks to both Auth and Query API directly. Deployed as its own Cloud Run service, same Always Free compute allowance as every other service here. **The one deliberately public service in this table** (§10.5) — real users and interviewers need to reach it directly from a browser, so it's the exception to every other row's "not publicly reachable," not an oversight. **Its outbound calls to Auth and Query API need explicit code, unlike the platform-native invoker relationships elsewhere in this table** (§10.5) — Cloud Scheduler and Pub/Sub automatically attach a signed identity token when they invoke a service, but the UI service calling another Cloud Run service via application code has no such automatic mechanism: its backend must explicitly fetch its own identity token (`google.oauth2.id_token.fetch_id_token()` against the metadata server) and attach it as a Bearer header on every call — including for its gRPC call to the Go Auth service, where the token goes in call metadata instead of an HTTP header — or those calls simply get rejected by the `--no-allow-unauthenticated` setting on the receiving end. **One real cost caveat, unique to this service**: Streamlit's live reactivity needs a persistent WebSocket connection, which conflicts with Cloud Run's scale-to-zero model — an idle-but-open browser tab keeps billing until Cloud Run's idle timeout closes it (verified: a documented real-world case shows bot/idle traffic on a public URL running up real, if modest, cost this way). Bounded with two Terraform settings (§10.5): a short idle/request timeout so no single connection can bill indefinitely, and `max-instances` capped low (this project never needs more than a couple concurrent demo sessions), which hard-limits worst-case exposure regardless of what hits the public URL |

## 8. Tech stack (proposed)

- **Language**: Polyglot by design (§6) — Python (FastAPI) for Processing, Query API, the daily batch job, and the UI (Streamlit); **Go + gRPC** for Auth; **Go** for the Poller. Python where the ecosystem matters (embeddings, RAG/LLM orchestration, dbt), Go where performance/concurrency matters (identity, polling) — not Go sprinkled everywhere, deliberately bounded to the two services that actually earn it (§6)
- **UI**: Streamlit — chosen over a full SPA framework (React/Next.js) because this project's actual demonstration value is the data/backend pipeline, not frontend engineering (matches the JD this project is built against, and the same right-size-the-effort reasoning applied to the materialized-view, Airflow, and DDD-proportionality decisions elsewhere in this doc). `st.chat_message`/`st.chat_input`/`st.write_stream` for the chat interface (confirmed native support for LLM streaming, see §4.4's streaming-endpoint requirement), plus standard Streamlit widgets/dataframes for watchlist management, the live feed, and stats — one app, one Cloud Run service (§6). Deployed with `--timeout` set low (a few minutes, not Cloud Run's multi-hour default) and `--max-instances` capped at 2 — bounds worst-case cost exposure from the WebSocket idle-billing caveat (§6) regardless of what traffic hits the public URL, without needing to gate the app behind platform-level IAM (which would block interviewers from opening it without your own gcloud credentials)
  - **Deliberate trade-off, considered and declined**: a custom lightweight frontend (FastAPI + HTMX, or plain HTML/JS) using SSE instead of Streamlit's persistent WebSocket would remove the idle-billing risk above almost entirely — SSE connections are naturally bounded to the duration of an actual query/response, not held open for a whole idle session. Declined in favor of Streamlit anyway: the risk is already bounded to near-zero for this project's realistic traffic, while dropping Streamlit reintroduces real frontend engineering effort — exactly what choosing Streamlit was meant to avoid in the first place. Simplicity over a marginal, already-mitigated cost risk, chosen consciously rather than left unexamined
- **Architecture pattern**: DDD + TDD apply to every service; **Clean Architecture's layered structure applies only to the Python services, not the Go ones** — this governs internal code structure within a service, orthogonal to the microservices split in §6 which governs boundaries *between* services. Rigor (and, for Python, the choice to use Clean Architecture's layering at all) is proportional to actual domain complexity, not applied uniformly — same reason this doc rejected a materialized view on a trivial query and Airflow for a 2-step DAG: a pattern earns its complexity where the underlying need is real, not by default
  - **Why Clean Architecture's layered folders apply to Python but not Go**: the classic domain/application/infrastructure/presentation split is a C#/Java-flavored convention, not an inherent requirement of "isolate business logic from infrastructure." Python/FastAPI's ecosystem is genuinely built for it — typed DI via `Depends()`, `Protocol`/ABC for interfaces, no fight against the language. It also doesn't hit the usual objection to layered folders (smearing multiple unrelated features across `domain/`, `infrastructure/`, etc.), because each Python service here is already scoped to one bounded context — there's only one feature per service to begin with. Go is different: its structural interfaces are idiomatically defined at the point of use, not in a shared abstraction layer, and its package-visibility model actively fights artificial layer boundaries (no "private-except-this-layer" — crossing a layer folder usually means exporting things that shouldn't be). Go achieves the *same underlying goal* (business logic that never touches Postgres/gRPC directly, fully testable, fully swappable) via its own idiom instead: one package per feature, interfaces defined next to their consumer, dependencies wired by hand in `main.go` — not a labeled "Clean Architecture" folder convention
  - **Full Clean Architecture layering — Processing (Python) only**: real, nontrivial domain logic worth isolating — the three-tier dedup logic (§4.3). Layers: domain (entities, business rules — no framework/DB/HTTP dependencies) → application (use cases orchestrating domain logic) → infrastructure (DB, external APIs, queue adapters — implements interfaces the domain layer defines) → presentation (FastAPI routes, request/response models)
  - **Lighter Clean Architecture structure — Query API (Python, v1)**: thinner in v1 — retrieval + LLM call plus watchlist management (§6), including the symbol-validation rule, but that's one validation function, not a rich rule set like Processing's dedup tiers — not enough on its own to justify full layering, though it's still the one piece of domain logic worth keeping isolated and unit-tested rather than buried in a route handler. Full tool-routing (Phase 2, §12.3) is where Query API *would* earn full layering. Forcing four formal layers onto a service this thin is scaffolding for its own sake — still tested, still built test-first, just without the full split
  - **Go-idiomatic structure, not Clean Architecture — Auth and Poller (Go)**: business rules (JWT-exchange logic for Auth; overflow-assignment ranking and cadence-scaling for Poller) live in a plain, dependency-free package, testable with no DB or HTTP mocking. Each package defines the interfaces it needs right where they're consumed (e.g. a `Repository` interface in the same file as the logic that calls it), not in a shared `domain`/`ports` package. Infrastructure (Postgres, gRPC, HTTP clients) implements those interfaces from the outside; nothing gets wired via a DI container — `main.go` constructs everything explicitly. Same testability and swappability Clean Architecture promises, achieved the way Go actually wants it done
  - **DDD**: the pure business-rule pieces already called out in §10.2 as pytest targets *are* the domain logic, regardless of language — the two-level dedup key and its "must not key on `source` or `symbol`" invariant (Processing, Python), the overflow-assignment ranking rule and cadence-scaling formula (Poller, Go), symbol validation (Query API, Python) — all kept persistence- and framework-agnostic, testable with no DB or HTTP mocking required
  - **TDD**: tests for the domain logic are written before the implementation, especially for the pieces above — their determinism (no I/O, no external state) is exactly what makes test-first practical rather than just aspirational. TDD applies across all services regardless of language or layering depth — it's the Clean-Architecture-vs-Go-idiom choice that varies, not the testing discipline
- **Queue**: **Corrected during implementation** — originally planned as Redis Streams or RabbitMQ locally, migrating to GCP Pub/Sub only at cloud deployment (both those local options are still valid on their own merits). Actually built with the **GCP Pub/Sub emulator locally**, not a stand-in broker: it speaks the real Pub/Sub client/server contract, including real push subscriptions (HTTP POST to a given endpoint) — Processing's `/pubsub/push` handler is called directly by the emulator exactly as real Pub/Sub will at cloud migration, with no separate bridging service and no rebuild needed when the deployment target changes, only environment/config. This was tried first with Redis Streams (needing a small bridging relay service, since Redis has no push delivery) — see `decision_log_claude.md` for the full trace of why the emulator replaced that design entirely. GCP Pub/Sub itself is confirmed permanent Always Free at 10 GB messages/month, see §6. AWS SQS dropped — see cloud-provider note below
- **Vector DB**: pgvector on **Supabase** free Postgres, preferred over Neon (doubles as article metadata store). Pinecone dropped — pgvector already covers the need, and Pinecone's free Starter tier auto-pauses indexes after 3 weeks of inactivity, an unnecessary gotcha for a project that isn't touched daily. Between Neon and Supabase, the gap is narrower than it first looks: Neon's free tier suspends compute after **5 minutes** of idle time, unconditionally, can't be disabled; Supabase pauses the whole project only after **7 days**. The poller's `SELECT DISTINCT symbol FROM watchlist` query (§4.2) runs unconditionally every 60s regardless of news volume — not gated on a "quiet news day" — so in practice **neither** timer fires under normal operation; this isn't really a quiet-stretch risk for either provider. **Confirmed, not assumed**: Supabase's own pause criteria count real database activity — direct queries or REST API calls that hit the database — not dashboard visits or requests that never touch the DB, and the poller's query qualifies. The residual, genuine difference is resilience to *poller downtime specifically*: if the poller service itself is down for 5+ minutes (bad deploy, Cloud Run incident), Neon autosuspends and cold-starts on recovery, while Supabase's 7-day window absorbs it without a hitch. Neon's database branching is a real plus if that dev workflow matters more than this narrow edge case
- **Embeddings**: sentence-transformers (local/free) or OpenAI embeddings API — the one accepted paid cost
- **LLM for answers**: OpenAI/Anthropic API, or a local model for cost control — the other accepted paid cost
- **Orchestration**: Docker Compose locally; Cloud Run for cloud deployment. **Every Cloud Run service and job defaults to request-only CPU allocation and min-instances=0 (scale-to-zero)** — confirmed these are Cloud Run's actual defaults, not something that needs to be specially configured, so leaving them alone (not explicitly setting "CPU always allocated"/instance-based billing or min-instances>0 anywhere) is what keeps Query API, Auth, and Processing free-tier-safe. Two service *shapes* are in play: the poller runs as a Cloud Run **Service** triggered via HTTP by Cloud Scheduler every minute (warm-instance reuse between triggers, no per-invocation secret refetch, see §4.2), while the daily batch runs as a one-shot Cloud Run **Job** (fine at once-a-day frequency, no reuse needed). This went through two corrections to land here — an earlier draft called the poller "always-on" (would have cost ~$65/month), the next draft made it a one-shot Job (would have blown the Secret Manager access-operations budget at every-minute frequency, §8's Secrets entry) — both are corrected throughout the doc now. AWS Fargate dropped — it has no free tier at all and would bill from the first container, unlike Cloud Run's permanent Always Free compute allowance. Airflow deliberately not used — see §4.6 for reasoning (a handful of sequential steps doesn't justify the operational weight, and Cloud Composer has no free tier)
- **Transformation**: dbt-core for the `prices` → `daily_symbol_features` model — free, no hosting cost, adds data tests and auto-generated lineage docs
- **Cloud provider**: GCP only, not split across AWS/GCP. AWS's Free Tier program was restructured in July 2025 — new accounts now get a time/credit-limited allowance rather than a guaranteed perpetual free tier, so S3/SQS/Fargate carry real cost risk for a newly created account. GCP's Always Free tier for the specific services used here (GCS, BigQuery, Cloud Run) is separate from its general trial credit and confirmed to persist after any trial period ends
- **Structured storage**: GCS (raw landing zone, Always Free 5 GB + lifecycle rule) and BigQuery (analytics/feature store, Always Free 10 GB storage + 1 TB query/month) — also directly satisfies the "GCP + BigQuery" cloud-familiarity target from the JD this project is built against
- **Secrets management**: **Google Secret Manager** — Always Free tier confirmed at 6 active secret versions and 10,000 access operations per month. This project needs exactly six: Finnhub API key, Marketaux API key, Google OAuth client secret (for `st.login()`'s `secrets.toml`, §3), the JWT signing secret (shared between Auth, which issues, and Query API, which verifies — see §6), the Supabase/Postgres connection string, and the LLM API key. That's the full free allocation with **zero headroom** — both enabled and disabled versions count toward the 6, so rotating even one secret creates a new version and pushes past the free tier unless the old version is deleted first, not just disabled. **What "past the free tier" actually costs, though**: $0.06 per extra active version per month — a seventh secret (e.g. a v2 need, §12) or a rotation that isn't cleaned up promptly is an administrative annoyance (delete the old version, or accept a few cents), not a real budget threat. Worth knowing precisely rather than either ignoring the cap or treating it as more dangerous than it is
  - **Access-operations budget depends on which Cloud Run shape fetches which secret.** Env-var secrets are fetched once per container start (confirmed). For request-driven Services with warm-instance reuse (Query API, Auth, Processing, UI, and now the poller — §4.2/§6) that's cheap: infrequent cold starts, not per-invocation. The one case that would have blown the budget: the poller was briefly a one-shot Cloud Run *Job* (no instance reuse between executions), which at an every-minute trigger cadence meant a fresh secret fetch on every single invocation — ~43,200/month against the 10,000 free, though even that overage would only have cost roughly $0.10–$0.40/month, not a meaningful sum. Fixed anyway by making the poller a Service instead of a Job (§4.2), removing the overage rather than just accepting a trivial cost
  - **The warm-instance assumption is "almost certainly," not "guaranteed"** (§4.2/§6's own wording) — Cloud Run can still cold-start a Service between triggers (traffic-based eviction, platform maintenance). That failure mode isn't unbounded, though: worst case, cold-starting on every single trigger is exactly the one-shot-Job scenario already costed above (~$0.10–$0.40/month). The Service-vs-Job fix changes the *typical* case from "always pay a little" to "almost never pay anything," not from "unbounded risk" to "bounded" — the bound already existed either way

## 10. Testing, CI/CD & infrastructure as code

### 10.1 Branching model
- `main` — always represents what's currently deployed to GCP. Protected branch: PRs require CI passing before merge
- `dev` — integration branch for local development, Docker Compose only. Never triggers a cloud deploy or `terraform apply`
- Flow: feature branches → PR into `dev` (verify locally with Docker Compose) → PR `dev` into `main` (triggers deploy)

### 10.2 Testing
- **TDD workflow**: tests for these pieces are written before the implementation, not after — see §8's "Architecture pattern" entry for why this is practical here specifically (domain-layer logic with no I/O to mock)
- pytest unit tests on the pieces with real logic to get wrong: the two-level dedup key (§4.3, including the "must not key on `source` or `symbol`" invariant), the overflow-assignment ranking rule (§4.2), symbol validation at watchlist add-time (§4.1), the cadence-scaling formula (§4.2), and JWT expiry/logout behavior (§3) — a request with an expired token must be rejected, and logout must discard the client-side token without expecting server-side revocation to do anything (there isn't any in v1)
- dbt's built-in data tests (not-null, uniqueness) cover the `daily_symbol_features` model (§4.6) directly

### 10.3 CI — GitHub Actions, runs on every branch and PR
- pytest + lint on every push, regardless of branch
- Optional: spin up the Docker Compose stack directly in the Actions runner and run a smoke/integration test against it — GitHub-hosted runners support Docker Compose natively, free, and gives `dev` real integration coverage beyond unit tests alone

### 10.4 CD — GitHub Actions, `main` only
- `terraform plan` runs on any PR targeting `main`, so the infra diff is visible in review before merge
- `terraform apply` plus the service deploy (Cloud Run services/job, Cloud Scheduler) run only after a merge lands on `main` — never triggered from `dev` or a feature branch
- GCP auth via **Workload Identity Federation**, not a long-lived JSON service account key — the trust binding is scoped specifically to the `main` branch, so a misconfigured workflow on any other branch can't authenticate to GCP at all
- **Push-based, not pull-based GitOps (e.g. ArgoCD) — a deliberate match to context, not a lesser option.** Pull-based tools reconcile a live Kubernetes API against Git continuously, which needs a cluster to run the reconciler in; fully-managed Cloud Run has no cluster for that to live in anyway. Pull-based drift detection also earns its complexity when multiple people might make untracked manual changes to shared infrastructure — not the case for a solo developer who is the only one with console access. Push-based CI applying on merge is the right-sized match here, not a compromise
- **Rollback story**: no separate tooling needed beyond what's already here — Terraform is declarative, so reverting the merge commit and letting CD re-apply restores the previous known-good state. Stated explicitly rather than left assumed

### 10.5 Infrastructure as code
- Terraform, single environment/state — no per-branch or per-environment workspaces, since there's genuinely only one deploy target, matching the single-branch CD gate above
- Resources managed: GCS bucket (+ lifecycle rule), BigQuery dataset/tables, Pub/Sub topic + push subscription (§6 — targeting Processing's endpoint, not a pull subscription), Cloud Run services (**auth**, query API, processing, UI, poller — request-only CPU, min-instances=0, defaults left alone across all five) plus one Cloud Run job (daily batch, once-daily), a Cloud Scheduler HTTP trigger for the poller (every minute) and a Cloud Scheduler job trigger for the daily batch (2 of the 3 free job definitions), the Workload Identity Federation trust, and the six Secret Manager secrets (§8) with per-service IAM bindings granting each Cloud Run service access only to the secrets it actually needs (e.g. the UI service gets the OAuth client secret, not the LLM API key)
- **Terraform manages the secret *containers* (the `google_secret_manager_secret` resource) and IAM bindings — never the secret values themselves.** The actual API keys, OAuth client secret, DB connection string, etc. are set out-of-band (`gcloud secrets versions add`, or the console), never passed through Terraform variables or `.tfvars`, and never committed to the repo. This is standard practice specifically because it's easy to get wrong on a first Terraform setup — the tempting shortcut of a `.tfvars` file with real keys in it defeats the entire point of Secret Manager and risks the values ending up in Terraform state or version control
- **Ingress/invocation IAM (§6) — public by default is not the assumption anywhere except one service**: every service is deployed `--no-allow-unauthenticated` except the UI service, which alone gets `--allow-unauthenticated` since real users need to reach it directly. Per-service `roles/run.invoker` bindings scope exactly who can call what: the UI service's own service account → Auth and Query API; Pub/Sub's push service account → Processing; Cloud Scheduler's service account → the poller (HTTP target) and the daily batch job. Nothing is reachable by the public internet except the one service that needs to be
- **The IAM binding alone doesn't attach the token — that split matters for what Terraform can and can't automate.** Cloud Scheduler → poller and Pub/Sub → Processing are platform-native invocations: configuring the service account on the trigger is enough, GCP attaches a signed identity token automatically, nothing to write. UI service → Auth and UI service → Query API are application code calling another Cloud Run service directly — Terraform can grant the IAM binding, but the UI service's own backend code still has to fetch and attach its identity token on every outbound call (§6), or the `--no-allow-unauthenticated` setting on the receiving end rejects it. This is an application-code requirement, not something the Terraform config itself can satisfy
- UI service additionally sets `--timeout` low and `--max-instances=2` (§8) to bound worst-case WebSocket idle-billing exposure
- Remote state stored in its own GCS bucket — trivial size, well within the same Always Free 5 GB tier already budgeted in §5

## 11. Out of scope

Three different claims are being made here, not one — labeled explicitly so "out of scope" doesn't get read as a blanket "yes, eventually" for all of it.

**Deferred — actively designed, will get built (v2, §12)**
- Everything in §12 (Phase 2): sentiment scoring, pattern detection, LLM tool-routing, twice-daily batch, historical backfill, JWT refresh flow. Fully designed already, deferred purely on sequencing — see §12 for the full detail.

**Acknowledged gaps — no active plan, but would matter for a genuinely production-grade system**
- Partial-failure / retry / dead-letter semantics across the processing pipeline (poller → queue → processing → embed → writes) — with this many moving pieces a real partial-failure story matters eventually, just not designed yet.
- Poller liveness/health monitoring — the stats dashboard (§4.6) and ingestion-lag logging (§4.3) both assume the poller is producing articles; neither would catch a *silent* failure mode where the poller keeps running "successfully" but produces nothing (e.g. a revoked Finnhub API key, or the API silently returning empty results).

**Not planned — no identified trigger, closer to permanent than "later"**
- Multi-provider login (email/password, other OAuth providers)
- Real-time push notifications to users
- Trading/brokerage integration
- Per-user data isolation beyond query-time filtering

### 12.1 Sentiment scoring
- Runs **FinBERT** (free, self-hosted, finance-tuned BERT sentiment model — same "free/local over paid API" reasoning as sentence-transformers for embeddings) once per article during processing (§4.3), storing a signed score (positive_prob − negative_prob) on `articles.sentiment_score`
- This is the input `daily_symbol_features.avg_sentiment` would aggregate via dbt — a column that doesn't exist in v1's schema and must be added back alongside this
- Adds a new dependency to the processing pipeline (FinBERT model weights, inference at ingestion time) — worth benchmarking latency impact on the processing service before committing to "once per article, inline"

### 12.2 Structured data extensions: twice-daily batch, backfill, pattern detection
- **Backfill, on first-ever add of a new symbol to any watchlist** (not per-user — matches §4.2's "shared, not duplicated" philosophy): an on-demand invocation of the batch job's container pulls the maximum ~1 year of daily candles from Finnhub's candle endpoint (`resolution=D`) in a single API call, populating `prices` retroactively so pattern detection has immediate context instead of waiting weeks to accumulate enough history, then immediately runs pattern detection for that symbol so it isn't left without a pattern flag until the next scheduled run
  - "First-ever add" needs a precise definition, not just "not currently on any watchlist": check whether `prices` already has continuous history up to yesterday for that symbol, not whether the symbol currently appears in the watchlist table. A symbol added, later removed by everyone, then re-added months later should have its `prices` gap backfilled (not skipped, since a hole in the middle would break the pattern window), not re-backfilled from scratch (wasteful, since existing rows are still valid, `prices` being append-only)
- **Scheduled runs, twice daily instead of v1's one** — two Cloud Scheduler triggers invoking the same Cloud Run job image in different modes:
  - **Morning run** (~09:35 ET, shortly after US market open): calls Finnhub's real-time `/quote` endpoint (not the daily candle endpoint) per watched symbol, capturing that day's opening price intraday. This exists specifically so "what did AAPL open at today" is answerable during market hours — v1's once-a-day run alone leaves "today" stale until evening
  - **Evening run**: unchanged from v1 — pulls the completed daily candle, finalizes `prices`, runs dbt — but now also runs pattern detection (below) afterward
- **Pattern detection**: **TradingPatternScanner** used from two triggers, same detection functions (`detect_wedge`, `detect_triangle_pattern`, `detect_head_shoulder`, etc.) either way:
  - **Nightly batch (evening run)**: runs detection once per symbol for each of a fixed set of common windows — **30 / 90 / 180 / 270 / 360 days** — writing results to `symbol_patterns`. Precomputes the fast-path cases (no window specified, or a round number matching how traders naturally think in months/quarters)
  - **On-demand (Query API's `get_pattern` tool, §12.3)**: for any window outside that fixed set, the same detection logic runs synchronously inside the live request, against a fresh slice of `prices` pulled for the exact requested window — not precomputed, not cached, computed fresh each time. This is what gives genuine "any X days" capability
  - Both paths are trivial compute regardless (pandas/numpy over at most a year of rows, no external API cost) — the split exists purely to keep the common case fast
  - **Both paths must exclude today's row until it's finalized.** The morning run only writes `open` for today — `high`/`low`/`close`/`volume` stay null until the evening run completes. The on-demand path can be triggered any time during market hours, so its query must filter to `date < today` (or the last date with a non-null `close`), so an incomplete row can never reach TradingPatternScanner and silently skew or break detection
  - `symbol_patterns` stores one row per detected pattern per symbol per window per day. A pattern's window always ends at the last *completed* trading day, never a partial one. Pattern detection is a heuristic, not ground truth — even human traders disagree on where a wedge starts/ends — so results should be surfaced with that framing, not as a confident fact
  - Explicitly not a hosted pattern-recognition API — none of the free-tier options found (Finnhub's own `/scan/pattern` appears premium-gated; Tickeron/TradingView are paid subscriptions) fit, and computing it locally against OHLCV already in the pipeline avoids a new API dependency entirely

### 12.3 LLM tool-calling / query routing
- The Query API gives the LLM three tools instead of always going straight to the vector store:
  - `search_news(symbols, query)` — the v1 RAG path, unchanged
  - `get_structured_data(symbols, metric, date=latest)` — reads `daily_symbol_features` / `prices`, filtered to the caller's watchlist:
    - `metric` is a defined enum tied to actual columns, not free text — `open_today | close_latest | volume_latest | price_change_pct | article_count | avg_sentiment | avg_ingestion_lag_seconds`
    - `date` (optional) lets the question target a specific past day ("last Tuesday"), not just the latest — without it, that kind of question has no way to be expressed. Defaults to the latest available date if omitted
    - If the requested `(symbol, date)` has no row at all, the tool returns nothing rather than a zero/null dressed up as data, so the guardrail can correctly say "no data that day" instead of implying a neutral reading actually occurred
  - `get_pattern(symbols, window_days)` — the two-tier fast-path/on-demand lookup described in §12.2, exposed as a callable tool
  - `symbols` is a list on all three tools, not a single ticker — a broad question like "any pattern forming today across my watchlist" passes the full watchlist into `get_pattern`, and `symbol_patterns` is sparse by design (one row only where a pattern was actually detected), so the result set of that single filtered query *is* the answer
  - The LLM decides which tool(s) to call per question — a pure news question calls `search_news`, a quantitative question calls `get_structured_data`, a pattern question calls `get_pattern`, a hybrid question can call several and synthesize across them
- **Freshness caveat**: "today" in a pattern or price question resolves to the most recently completed batch run (the evening run), not literally the current moment. If asked before that run has completed for the current day, the answer reflects the prior completed day's data — the response must state which date it's actually reflecting rather than silently presenting stale data as if it were live
- Extends v1's guardrail: if none of the three tools return anything relevant, the LLM must say so rather than speculate
- Query API service gains the TradingPatternScanner dependency for its on-demand pattern path, not just the nightly batch job

### 12.4 Extended testing for v2
- `get_pattern`'s window-snapping and fast-path-vs-on-demand branching logic — exact matches to the 5 precomputed windows and the default-to-180 case must hit the precomputed lookup, everything else must hit the on-demand path, including the boundary cases right at 30/90/180/270/360
- The today's-partial-row exclusion rule in pattern detection — a row with nulled `high`/`low`/`close`/`volume` must never reach TradingPatternScanner, on both the nightly and on-demand paths
- `get_structured_data`'s metric-enum validation, `date` handling (including the default-to-latest case), and missing-row behavior — a `(symbol, date)` with no data must return nothing, never a null/zero dressed up as a real reading
- **Tool-routing itself is evaluated separately from unit tests** — a small labeled set of sample questions (pure news, pure quantitative, pure pattern, hybrid) checked against which tool(s) the LLM actually calls, since "does the LLM pick the right tool" is a behavioral/eval question, not a deterministic unit test
- The backfill gap-detection logic (§12.2) — a re-added symbol with an existing partial history should backfill only the gap, not the full year, and not skip entirely
