## Implementation (post-milestone-4 — Redis Streams + relay replaced by the real Pub/Sub emulator)

User-directed course correction (logged in full in `decision_log.md`): switched the local queue from Redis Streams + a bridging relay service to Google's real Pub/Sub emulator, which supports genuine push subscriptions. Concrete implementation trace:

- **Image**: `thekevjames/gcloud-pubsub-emulator:latest` — chosen over the official `google/cloud-sdk:emulators` tag, which has a history of being flaky/inconsistently maintained across SDK releases (a known GitHub issue on `GoogleCloudPlatform/cloud-sdk-docker`). This community image is a thin wrapper around the same `gcloud beta emulators pubsub start` binary.
- **Bug in my first attempt, caught before ever running it**: guessed the image's config approach as `PUBSUB_PROJECT1=<project>` env var, matching a half-remembered convention. Verified against the actual image source before using it — that env-var format is real, but is **pull-subscriptions only**; push subscriptions require a mounted JSON config file (`PUBSUBC_CONFIG` pointing at a file with `push_config.push_endpoint` per subscription). Also initially guessed the port as `8085` (real Pub/Sub's actual port) — the emulator image itself listens on `8681`. Both caught by researching the image's actual source/README before wiring docker-compose, not by a live failure — worth noting as the discipline that should apply *before* the "verify live" step, not instead of it.
- **Config schema** (`infra/pubsub-emulator/config.json`): an array of `{project, topic, subscriptions: [{name, push_config: {push_endpoint}}]}` objects — verified against the tool's actual Python source (`pubsubc.py`) rather than assumed, since a guessed schema here would fail silently (wrong keys just get ignored, not rejected) rather than erroring loudly.
- **Go client**: `cloud.google.com/go/pubsub/v2` (not v1 — v1 is in maintenance-only mode through Dec 2026, v2 is where Google points new code). `PUBSUB_EMULATOR_HOST` env var is all `pubsub.NewClient` needs to redirect at the emulator instead of real GCP — no code branching for emulator-vs-real, confirmed by the client library's own behavior when that env var is set.
- **Verified live, multiple times, including the actual point of the whole change**: a real poll cycle publishing 15 Finnhub articles were pushed by the **emulator itself** (confirmed via the emulator container's IP appearing as the caller in Processing's access logs, not the poller's) directly to Processing's unchanged `/pubsub/push` endpoint — zero relay, zero Redis, genuine push delivery working end to end locally.
- **Deleted**: `services/relay/` (entire service), `services/poller/internal/poller/redis_publisher.go` and its test, the `redis`/`relay` docker-compose services, the `github.com/redis/go-redis/v9` dependency (removed by `go mod tidy` once nothing imported it).
- **Kept for reference, unused in `main.go`**: `processing_client.go` (the milestone-1-3 direct-HTTP-to-Processing publisher) — same reasoning as before, demonstrates the pre-queue approach, still fully tested.

## Implementation (milestone 4 — Microservices split)

- **Major bug found via live verification: `find_by_fuzzy_key` matched a newly-inserted article against itself, so every article without a canonical URL was silently never embedded.** `_resolve_article`'s tier-3 fallback (`process_article.py`) calls `find_by_fuzzy_key` immediately after `insert_by_content_hash` succeeds, to check for a cross-source match — but the query had no exclusion for the row it had just inserted in the same transaction. Since that row's own `normalized_headline`/`published_at` trivially satisfy the fuzzy-match `WHERE` clause, every URL-less article "found" itself, was marked `is_new=False`, and the already-computed embedding was silently discarded — reproduced and confirmed directly: `insert_by_content_hash` → `inserted=True`, then `find_by_fuzzy_key` → returns its own just-created `article_id`. **Only affected articles with no `canonical_url`** (URL-bearing articles take tier 1's path and never call `find_by_fuzzy_key` at all) — which is exactly why milestone 1-3's manual verifications (which happened to use articles with URLs) never surfaced it, and why the real Finnhub poll cycle's 15 AAPL articles *did* have embeddings (their raw payloads happened to include `canonical_url`) while manually-injected test articles without one did not.
  - **Why no unit test caught this**: `FakeRepo`'s `by_hash` and `by_fuzzy` were separate dicts, with `register_fuzzy_key` populating the second one as an explicit, decoupled step the use case calls — so the fake could never reproduce "the fuzzy lookup query naturally finds the row `insert_by_content_hash` just wrote," because in the fake those were two unrelated operations. Real Postgres has one `articles` table; a row inserted by hash is immediately visible to a fuzzy `SELECT` in the same transaction. Fixed the fake to model a single shared `rows` dict indexed by article_id, matching reality, and added `TestTier2ContentHash::test_brand_new_article_with_no_url_still_gets_embedded` — confirmed this test genuinely fails without the fix (`0 == 1`, reproducing the exact production symptom) and passes with it.
  - **Fix**: `find_by_fuzzy_key(fuzzy_key, exclude_article_id)` now takes and excludes the calling article's own ID (`domain/repository.py`'s protocol, `postgres_repo.py`'s `AND id != CAST(:exclude_article_id AS uuid)`, `process_article.py`'s call site passing `article_id`).
  - **Blast radius, checked directly, not assumed**: `SELECT count(*) FROM articles WHERE canonical_url IS NULL AND NOT EXISTS (SELECT 1 FROM embeddings WHERE article_id = articles.id)` returns **0** as of this fix — the bug was live only briefly within this same working session (introduced by the two-phase dedup design, smell-audit fix #6, caught by this session's own milestone 4 cross-source-dedup verification), and the only articles it actually affected were this session's own manual test rows, already cleaned up. No real ingested data was silently lost. Still worth the fix and this record, since the same gap would have compounded silently once the poller ran unattended against real Finnhub/Marketaux articles lacking a `canonical_url` (Marketaux articles in particular, which don't always expose one).



- **Bug caught by live verification**: the relay's live logs (once actually run against a real Redis in docker-compose, not just unit tests against fakes) showed every single `XReadGroup` call failing with `i/o timeout`, even though nothing was actually wrong with Redis or the query. Root cause: go-redis's client-side `ReadTimeout` defaults to 3 seconds, shorter than the `Block: 5000` (5s) argument passed to `XReadGroup` — the client gave up on the underlying socket read before Redis's own server-side block window had a chance to elapse and return "no new messages." Fixed by explicitly setting `ReadTimeout` on the client to exceed the block duration (`blockDuration + 2*time.Second`). This is a well-known but easy-to-miss gotcha with any blocking Redis command (BLPOP, XREAD BLOCK, etc.) through a client library — the client's own read timeout must always be configured longer than any blocking command's wait window, or the setup looks broken (spurious timeouts on every call) when the actual query/config was fine. Caught immediately by watching real container logs, not by the unit tests (which use fakes and never touch a real client timeout).

- **Bug caught by live verification, in the test itself, not the production code**: `redis_publisher_test.go`'s original read-back logic used Redis Streams' `"$"` special ID ("only messages after this XREAD call starts") to isolate the test's read from pre-existing stream entries. That's a race: `Publish` had already completed by the time the blocking `XREAD` actually began, so `"$"` resolved to a point *after* the message was written, and the read-back missed it entirely — confirmed by checking Redis directly with `XRANGE`, which showed `RedisStreamPublisher.Publish` had, in fact, written the message correctly. Fixed by recording the actual last entry ID *before* publishing (`XREVRANGE ... COUNT 1`) and reading strictly after that fixed point instead of a moving "now" — deterministic instead of racy, and faster too (0.04s vs. 3.4s, since it no longer needs to block waiting for a message it already missed).

- **The Redis Stream name (`"articles"`) is duplicated as an untyped string constant in two separate Go modules** (`poller/internal/poller/redis_publisher.go`'s `RedisStreamName`, `relay/internal/relay/redis_reader.go`'s `StreamName`) with no compile-time link between them — poller and relay are genuinely separate services/modules, so there's no shared package to import a single constant from without adding a third shared module just for this one string. A rename in one place wouldn't fail the build, it would just silently stop messages from ever being read. Accepted as-is (a shared internal Go module across two otherwise-independent services would be its own new coupling to maintain, for one constant), but flagged here explicitly since it's exactly the kind of drift a future edit could introduce without any test catching it — the live end-to-end test (poller → redis → relay → processing) is what actually guards this, not the type system.

## Implementation (milestone 3 — Dynamic symbol coverage)

- **Marketaux live check completed (docs/milestone.md §3's required live check, the spec's own flagged highest-risk assumption) — findings meaningfully differ from the spec's conservative assumption.** Made real calls against `https://api.marketaux.com/v1/news/all` with a real API key:
  - **Per-request symbol limit: the spec's assumed 20-symbols-per-call batching is far more conservative than necessary.** A single request with 98 distinct symbols returned `200 OK` with a proportionally larger `meta.found` count as symbols were added (25 symbols → 569,593 matches; 40 → 642,824; 98 → 852,885), and a symbol near the *end* of the 98-symbol list (`RMD`, position 84) was independently confirmed to return real matching articles when queried alone — strong evidence the full batch is genuinely searched, not silently truncated server-side. Marketaux's docs state no explicit limit at all (confirmed via a live docs fetch, not just the earlier "docs block automated fetching" note) — the practical limit, if one exists, is well above 98 and wasn't found by this test. **Recommend revisiting `MarketauxSymbolsPerCall = 20` in `cadence.go`** — a much higher batch size (e.g. 50-100) would need far fewer daily calls for the same overflow coverage, meaningfully improving the achievable cadence. Left at 20 for now pending a decision on how aggressive to be without a confirmed hard ceiling; flag this for the user to weigh in on before the Marketaux client is built.
  - **Daily quota reset boundary: genuinely undocumented, confirmed by exhausting headers, not just docs.** `x-usagelimit-remaining` counts down (100 → 92 after 8 test calls) but no reset-timestamp header exists anywhere in the response (checked full unfiltered headers). Cloudflare-fronted (`server: cloudflare`), no `Retry-After` or `X-RateLimit-Reset`-style header present. This can only be determined by watching the counter reset over real time (exhaust it, note the wall-clock timestamp when `remaining` returns to 100) or contacting Marketaux support — not resolvable from a single live check. The spec's cadence formula assumes a smooth daily budget either way, which remains a reasonable working assumption regardless of which reset model turns out to be true, per the spec's own §4.2 reasoning.
  - Separately confirmed: `x-ratelimit-limit: 30` is a **rolling 60-second** short-window cap (distinct from the 100/day quota) — not previously surfaced in this project's docs, worth being aware of when building retry/backoff logic for the eventual Marketaux client.
  - 8 of the free tier's 100 daily calls were spent on this verification (92 remaining at time of writing) — a real, deliberate cost the live check itself required, consistent with the spec's own framing that this check "should happen early" precisely because it's cheap in absolute terms.
- **Marketaux client (`marketaux.go`) built and verified against the real live API, not just fakes** — a scratch verification binary (deleted after use, not committed) confirmed the actual Go client correctly authenticates, batches, and parses a real response: 3 real news items returned for AAPL, including correct timestamp parsing (`2026-09-20T06:00:55.000000Z` → `2026-09-20 06:00:55 +0000 UTC`) using the microsecond-precision layout confirmed during the live check above (`marketauxTimeLayout`, distinct from Go's standard RFC3339). `MarketauxSymbolsPerCall` set to 50 per the user's explicit choice (moderate increase from the spec's original 20, given real evidence up to 98 works but only that one high value was tested).

- **Manual live verification of `/trigger` left orphaned watchlist/user rows in the shared dev Postgres, breaking a later integration test run** — seeded a real user + AAPL watchlist row by hand to prove the poller's real Finnhub call path and partial-failure handling (verified: real request hit Finnhub, got a real 401, cycle still returned 200). Cleanup afterward missed the actual row (deleted the wrong/nonexistent id first), leaving a stale watchlist row that inflated `TestDistinctWatchedSymbols_AggregatesWatcherCountAndEarliestAddedAt`'s AAPL watcher count from 2 to 3 on the next run. Same root cause as milestone 1's cross-suite Postgres interference, different trigger (manual poking instead of concurrent test runs) — reinforces that this shared local dev database has no isolation, so any manual verification against it needs the same care as a test fixture about cleaning up exactly what it added.

- **`RunCycle`'s Finnhub lookback window is hardcoded to 24 hours per cycle (`cycle.go`)** — §4.2 doesn't specify a from/to window for the company-news call explicitly, so this was picked rather than derived. A full day's lookback on a 60-second poll cycle means the same article can appear in Finnhub's response on many consecutive cycles; this is intentional and harmless given dedup (§4.3) makes re-seeing an already-published article a no-op, not a correctness risk — but the window itself (why 24h and not, say, 1h or the poll interval) is a judgment call worth a second look once real Finnhub responses are available to check how far back `company-news` actually returns meaningfully fresh items.

- **Cadence-scaling formula derived as `(1440 / 100) * calls_per_cycle` minutes** — §4.2 states rounded examples ("~14 min at ≤20 overflow symbols, ~28 min at ~40") but not the exact formula. Derived it as: the 100-call/day Marketaux budget spread evenly across a day (1440 minutes/day ÷ 100 calls = 14.4 min per call-slot), multiplied by how many calls one cycle now needs (`ceil(overflow_count / 20)`). This reproduces the spec's own examples almost exactly (14.4 ≈ "~14 min", 28.8 ≈ "~28 min") and generalizes correctly to any overflow count. Flagging since this is a formula I derived to match given examples, not one stated explicitly in the spec — worth a second look if the actual live Marketaux behavior (reset boundary, real per-call symbol limit) turns out to differ from the assumed 100/day-smooth-budget model once verified.

- **Finnhub client verified live once a real API key was provided** — triggering a real poll cycle for AAPL against the real `https://finnhub.io/api/v1/company-news` endpoint returned 13 real news items, all correctly parsed by the documented-only struct and published through the full real pipeline (Processing → dedup → embed → Postgres) with zero errors. Confirms the `related` field's exact type didn't matter for parsing correctness (never accessed downstream) and that `datetime` (Unix seconds) parses correctly. Closes the "response-parsing unverified" gap noted below.
- **Bug caught during this verification, not in application code**: a stray local `go run ./cmd/server` process from an earlier manual test session was still listening on `0.0.0.0:8080`, silently intercepting `curl localhost:8080` requests meant for the real Docker container (`127.0.0.1:8080`, a separate listener) — `docker logs` showed no activity despite `curl` returning `200`, because the request never reached the container at all. `pkill -f "go run ./cmd/server"` had not actually killed it, since `go run` spawns a separate compiled child binary (`server.exe`) that a pattern match on the parent command doesn't catch. Found by checking `netstat` for a second, unexpected listener on the same port. Lesson: after `go run` during manual testing, verify the actual child process is gone (`tasklist`/`ps`) before assuming a `pkill` on the `go run` invocation cleaned it up.
- **Finnhub client's response struct is built from documentation only, not verified against a live call** — no Finnhub API key was available. A research pass confirmed the endpoint (`GET /company-news?symbol=&from=&to=&token=`), field names (`category`, `datetime`, `headline`, `id`, `image`, `related`, `source`, `summary`, `url`), and that `datetime` is Unix seconds, from Finnhub's docs page's Response Attributes section directly. One field's exact JSON type isn't 100% pinned by the docs text itself: `related` (comma-separated string of symbols, per Finnhub's general convention, but not explicitly typed in the docs prose) — modeled as `string` here. **Must be verified against a real API response once a key is available** — if `related` turns out to be a JSON array instead of a comma-joined string, `companyNewsItem.Related` needs to change from `string` to `[]string`.

## Smell audit fixes (post-milestone-2, user-requested)

The #2 schema change (`articles.normalized_headline NOT NULL`) broke query-api's own integration test fixture (`tests/integration/test_end_to_end.py`'s `seeded_article`), which seeds a raw article row directly via SQL and predated the new column — caught immediately by rerunning the full suite after the fix, not assumed clean. Fixed by having the fixture populate `normalized_headline` itself with a literal value, rather than importing processing's `normalize_headline()` across the service boundary for a value this particular test never exercises for fuzzy matching anyway.

Note: the auth Go module's import path was renamed to `stock-news/auth` outside this session (the user renamed the project's database/module names directly on disk between turns). Editing `cmd/server/main.go` for #3 without first checking for this reintroduced the previous, now-stale import path there and in `internal/auth/grpc.go`, `internal/auth/grpc_test.go`, and `tests/integration/end_to_end_test.go` — caught immediately by `go build ./...` right after the edit (which is exactly why that check happens after every change, not at the end of a session) and fixed by updating all four files' imports plus regenerating `proto/auth/v1/auth_*.pb.go` from the already-correct `.proto`. Lesson: when a background note says a file changed on disk for an unrelated reason, check whether it signals a broader rename before editing nearby files that might reference the old name.

User asked for a critical pass over the codebase for smelly/unsound decisions. Six items were found and fixed; each verified live against real Postgres, not just unit tests.

- **#1 — Processing's dedup insert had an unhandled race that could 500 the request.** `insert_by_canonical_url`/`insert_by_content_hash` did `INSERT ON CONFLICT DO NOTHING` then a separate `SELECT` on miss; a concurrent insert landing between those two statements could make the `SELECT` return zero rows (`existing[0]` → `TypeError`). Fixed by switching both to `ON CONFLICT DO UPDATE SET <col> = EXCLUDED.<col> ... RETURNING id, (xmax = 0) AS inserted` — one atomic round trip, same pattern already proven in auth's `PostgresRepository.Create`. `(xmax = 0)` is Postgres's standard trick for "was this row just inserted, or did the conflict clause update an existing one" — verified directly against real Postgres (a scratch table, insert-then-conflicting-insert) before trusting it. Also verified with a real 10-thread concurrent-write integration test (`tests/integration/test_concurrency.py`) hitting live Postgres: no crashes, all 10 calls agree on one article id, exactly one row.
- **#2 — Fuzzy-match normalization diverged between Python and SQL.** `domain/dedup.py`'s `normalize_headline` (ASCII `string.punctuation`) and the old SQL-side `regexp_replace(headline, '[^\w\s]', ...)` are not equivalent for non-ASCII headlines (curly quotes, em-dashes, accents — exactly what real news APIs produce), silently breaking tier-3 cross-source matching. Fixed by adding a `normalized_headline` column to `articles`, computed once in Python at insert time and matched with plain equality in SQL — no second normalization implementation to keep in sync. Required a schema change (`infra/postgres/init.sql`) and recreating the local Postgres volume (user confirmed OK — local dev/test data only).
- **#3 — No warning if the JWT secret is still the hardcoded dev default at startup.** `"dev-secret-change-me"` is a reasonable *default*, but nothing flagged it if it survived into a real run — silent total-auth-bypass risk (HS256 is symmetric; the string is public in this repo). Fixed by adding a startup warning in both query-api (`presentation/api.py`, checked against `DEFAULT_JWT_SIGNING_SECRET` in `settings.py`) and auth (`cmd/server/main.go`), mirroring the existing `ANTHROPIC_API_KEY`-unset warning pattern.
- **#4 — Auth's gRPC port had no boundary in local docker-compose.** `ExchangeIdentity` trusts whatever `google_sub`/`email` the caller sends (by design — Google verification happens in `st.login()`, not Auth; real enforcement is Cloud Run IAM in the target deploy). Locally, `50051:50051` published to `0.0.0.0` meant anything on the local network could mint a valid 24h JWT for any user. Full ID-token verification in Auth would duplicate what IAM already guarantees in the real deploy and wasn't attempted; instead, bound the port to `127.0.0.1` only in `docker-compose.yml` — closes the local-network exposure without changing the service's actual contract or requiring a design only relevant to a deployment target this project doesn't run in.
- **#5 — No non-root user in any of the four Dockerfiles.** Inconsistent with how carefully this project treats hardening elsewhere (per-service IAM, Workload Identity Federation, no long-lived keys). Added a dedicated `appuser` (Python services, needs `/app` write access for `uv`) or Alpine's built-in `nobody` (auth's static-binary final stage, no write access needed) to all four Dockerfiles.
- **#6 — No transaction spanning article-insert + symbol-link + embedding-write.** Each was a separate `engine.begin()` call; a crash mid-sequence left an article that exists but has no embeddings, permanently invisible to retrieval with no error (this exact gap is §11's accepted "no partial-failure/retry semantics," but leaving it live and undetected is worse than it needs to be for a fix this cheap). Fixed with a `UnitOfWork` (`domain/repository.py`'s protocol, `infrastructure/unit_of_work.py`'s Postgres implementation) — `PostgresArticleRepository`/`PostgresEmbeddingWriter` now take a `Connection` instead of opening their own `engine.begin()`, and `ProcessArticleUseCase` wraps insert+link+embed-write in one transaction. **This surfaced a second real design question**: embedding is CPU-bound and shouldn't happen inside an open DB transaction (pool exhaustion risk), but embedding *before* the transaction meant a duplicate article got embedded once wastefully — violating §4.3's "no re-embed on a cross-match" guarantee a different way. Resolved with a two-phase design (user's explicit choice over accepting the wasted embed): a cheap read-only `DedupPrecheck` (`infrastructure/dedup_precheck.py`) runs first, outside any transaction, and only a genuinely-new article reaches the embed call; the transaction afterward still re-verifies uniqueness atomically, discarding the just-computed embedding (not re-fetching or erroring) in the rare case a concurrent writer won the race in between. Added `tests/application/test_process_article.py::TestRaceBetweenPrecheckAndTransaction` as a unit-level regression test for that exact race.

## Implementation (milestone 2 — Auth)

- **Bug caught by live verification**: `app.py` used `st.user.is_logged_in` (attribute access), which crashed with `AttributeError`/`KeyError` when no `secrets.toml` `[auth]` block is configured — confirmed against Streamlit's own source (`UserInfoProxy`): `is_logged_in` "does not exist" at all until `st.login()` is configured, it isn't just `False`. `st.user` is a read-only `Mapping`, not a plain object, so the safe check is `st.user.get("is_logged_in", False)`, which degrades correctly to "not logged in" instead of crashing when OAuth isn't configured yet (this project's actual current state, since real Google OAuth credentials require Google Cloud Console setup outside this session's reach). Caught only by actually running `streamlit run app.py` and loading the page in a browser — pure code review would have missed it, since `st.user.is_logged_in` reads as ordinary, unremarkable attribute access.
- **Bug caught by live verification**: the containerized UI crashed with `StreamlitAuthError` ("configure credentials... in secrets.toml") even after the user filled in a real `services/ui/.streamlit/secrets.toml` — because `services/ui/.dockerignore` deliberately excludes `secrets.toml` from the build context (the right call: never bake real OAuth credentials into an image layer), but `docker-compose.yml`'s `ui` service had no corresponding runtime mount to compensate. The file existed on the host and worked fine when running `streamlit run app.py` directly (no Docker), which is exactly why this didn't surface until testing the actual containerized path specifically. Fixed by bind-mounting `./services/ui/.streamlit/secrets.toml:/app/.streamlit/secrets.toml:ro` in `docker-compose.yml` — read-only, host file only, never copied into the image.
- **OAuth handshake verified live once the user supplied real Google Cloud Console credentials** — with `services/ui/.streamlit/secrets.toml` filled in (client_id/client_secret from a real OAuth 2.0 Client ID, redirect URI `http://localhost:8501/oauth2callback` matching what was registered in Google Cloud Console), clicking "Log in with Google" correctly redirects to Google's real sign-in page ("Sign in to continue to stock-news"), confirming client ID, redirect URI, and OAuth config are all correctly wired end to end. Did not complete an actual sign-in (that would mean acting on the user's real Google account credentials autonomously) — the redirect reaching Google's real consent screen is the verification boundary; completing the full round-trip (callback → `st.user` populated → UI calling Auth's `ExchangeIdentity`) is the user's own action to take, not something to automate.
- **Bug caught by live verification**: clicking "Log in with Google" crashed with `StreamlitMissingAuthlibError` — `st.login()`/`st.user` require the `streamlit[auth]` extra (pulls in `authlib`), not plain `streamlit`. Fixed by pinning `streamlit[auth]>=1.64.0` in `pyproject.toml`. Caught by actually clicking the button in a browser, not by the app booting successfully — the pre-login screen renders fine either way, so this only surfaces once `st.login()` itself actually executes.

- **`PostgresRepository.Create` uses `ON CONFLICT (google_sub) DO UPDATE SET google_sub = EXCLUDED.google_sub ... RETURNING`, not a plain `INSERT ... ON CONFLICT DO NOTHING`** — the service layer's `FindByGoogleSub`-then-`Create` isn't atomic (Cloud Run scales this service by default, same reasoning as Processing's dedup race in §4.3), so two concurrent first-logins for the same brand-new user can both reach `Create`. A plain `DO NOTHING` would make the second caller's `RETURNING` clause return zero rows, which need extra handling to fall back to a lookup. The no-op `DO UPDATE` keeps `RETURNING` always returning the (now-existing) row in one round trip, so both concurrent callers get the same correct `User` back with one code path instead of an insert-then-conditionally-lookup branch.
- **JWT signing uses HS256 with a shared secret, not RS256 with a public/private keypair** — simpler for v1 (one shared Secret Manager value both Auth and Query API read, §8), matches "shared JWT signing secret" language already in `decision_log.md`/`api-spec.md`. Acceptable since both signer and verifier are services this project controls; RS256 would only earn its complexity if a third party needed to verify tokens without holding the signing secret.
- **`JWTSigner.Parse` lives in the `auth` package's `internal/auth`, but Query API needs the same verification logic** — rather than Query API importing Auth's Go module (crossing a service boundary, and Query API is Python anyway), Query API gets its own `jwt_verify.py` implementing the same HS256-verify-with-shared-secret contract independently, per `project-structure.md`'s existing plan (`infrastructure/jwt_verify.py`). The two implementations are kept in sync by both being tested against the same claims shape (`sub` = user ID, `exp` = expiry) rather than by sharing code, since there's no practical way to share code across a Go/Python boundary here.

- **UI's generated Python gRPC stubs (`auth/v1/auth_pb2*.py`) live directly under `services/ui/`, not nested inside `clients/`** — `grpc_tools.protoc`'s generated `_grpc.py` file always imports its message module with an absolute import matching the `.proto`'s package path exactly (`from auth.v1 import auth_pb2`), regardless of where `--python_out` writes the files. Placing the output under `clients/authv1/auth/v1/` (to keep generated code visually grouped with the other client code) broke that import at runtime — `auth.v1` wasn't importable from that nesting depth. Fixed by generating directly to `services/ui/` so `auth/v1/` sits at the import root the generated code actually expects. Caught by trying to import the client module, not by the generation step succeeding — `protoc` has no way to know whether its own output will be importable from wherever you point `--python_out`.

## Implementation (v1 build)

- **`processing`'s and `query-api`'s integration tests share one live Postgres and must not run concurrently** — both write to and truncate the same `articles`/`article_symbols`/`embeddings` tables (each service's own module-scoped fixture cleans up after itself, but has no idea the other service's suite might be running against the same database at the same time). Confirmed by reproducing a one-off failure that only appeared when both suites' background runs overlapped, and which disappeared entirely once re-run sequentially. Acceptable for now (single-developer local docker-compose, milestone 1 scope) — revisit if CI (§10.3) ever runs these two suites in parallel jobs against a shared database instead of isolated ones.

- **Embedding model: `sentence-transformers/all-MiniLM-L6-v2`** — 384-dim output, small/fast enough to run locally with no GPU and no per-call cost (matches §8's "local embeddings" pick). `embeddings.vector` is declared `vector(384)` in the schema specifically because this model was chosen; changing the embedding model later requires a migration to resize the column, not just a code change.
- **Dedup domain functions split into three independent building blocks (`content_hash`, `fuzzy_key`, canonical URL is just `article.canonical_url`), not one `dedup_key()` fallback function** — the spec's tier 2 (content hash) and tier 3 (fuzzy) aren't a strict fallback chain: tier 2 is a hard DB uniqueness constraint (exact match only), tier 3 is a best-effort in-app lookup that runs *in addition to* tier 2, not only when tier 2 misses (a genuinely new article still needs its fuzzy key registered so a later cross-source poll can find it). Modeling them as separate functions the application layer composes matches this correctly; a single chained function would have hidden the bug where two different-hash articles both look "new" from tier 2's perspective alone.
- **`register_fuzzy_key` is a separate repository method from insert, not bundled into `insert_by_content_hash`** — keeps the fuzzy-key bookkeeping explicit in the use case (`process_article.py`) rather than silently baked into an insert path, so it's obvious from reading the use case that tier 3 is a distinct, best-effort step per §4.3 ("can't be a hard constraint").
- **`torch` pinned to the CPU-only wheel index (`pytorch-cpu` via `tool.uv.sources`), in both `processing` and `query-api`** — by default `uv`/pip resolve `torch` (a `sentence-transformers` dependency) to its CUDA-enabled build, which pulls ~2GB of NVIDIA driver packages (`nvidia-cudnn`, `nvidia-cublas`, `nvidia-cusolver`, etc.) neither service needs, since embeddings run as local CPU inference here (no GPU in this deployment target, §8). Discovered when a Docker build that should take under a minute for these already-cached layers was instead downloading 2GB+ of CUDA packages inside the container every time — caught by watching `docker compose build --progress=plain`'s actual output, not by the build merely succeeding. **`tool.uv.sources` alone didn't work** — it only reliably applies to a package uv resolves as a direct dependency; torch was only ever a *transitive* dependency of `sentence-transformers`, so the source override was silently ignored (still resolving from PyPI's default index, still CUDA). Fix required also adding `torch>=2.2` explicitly to `[project.dependencies]` so uv treats it as directly pinned and actually applies the index override — cut processing's locked package count from 85 to 67.
- **Bug caught by live verification, not unit tests**: neither `processing` nor `query-api` had a `.dockerignore`, so `COPY . .` in their Dockerfiles (which runs *after* `RUN uv sync --frozen --no-dev` at build time) copied the host's own `.venv/` — a Windows-native venv built by local `uv sync` during development — straight over the correctly-built Linux venv inside the image. Every container start then had `uv run` detect a broken/mismatched venv and silently reinstall everything from scratch (including a ~3.4GB torch/sentence-transformers reinstall), turning `docker compose up` on an already-built image into a multi-minute reinstall instead of an instant start. Fixed by adding `.dockerignore` (`.venv/`, `__pycache__/`, `tests/`) to both services. Caught only by actually running `docker compose up` and watching container logs — a build succeeding says nothing about whether the resulting container starts fast or correctly.
- `PostgresArticleRepository.find_by_fuzzy_key`'s SQL used `:published_date::date` (bind-param immediately followed by a `::cast`) — SQLAlchemy's `text()` parses this as the start of a second, malformed bind-param token, so the query raised a syntax error against real Postgres despite passing every unit test (which use an in-memory fake repo, not real SQL). Fixed to `CAST(:published_date AS date)`. Caught only once `services/processing/tests/integration/test_end_to_end.py` ran against the real docker-compose Postgres — the exact scenario backend-service-delivery's §2 exists for (fakes prove the code does what its author believed, not that it works against the real dependency).
- **LLM provider: Anthropic (`claude-haiku-4-5`), and the spend-ceiling guardrail catches both `PermissionDeniedError` and `RateLimitError`** — the provider-side spend cap (§4.4, §5) doesn't expose a distinct "billing cap hit" exception; Anthropic's SDK surfaces a hard cap as `PermissionDeniedError` (401/403-class) and can also present as `RateLimitError` depending on how the cap is configured on the account. Both map to the same honest "spending cap reached" user-facing message rather than a generic error, since from the caller's side they're indistinguishable in effect (no further calls will succeed until the cap resets) even though only one is the "true" cap-exceeded signal.
- **Bug caught by live verification**: `AnthropicLLMClient` crashed with an unhandled `TypeError` from deep inside the Anthropic SDK when `ANTHROPIC_API_KEY` was unset (a local-dev/cost-sensitive scenario, not a real deploy) — the client's `except PermissionDeniedError`/`RateLimitError` guardrail only covers failures from an actual API *response*, not a request that never gets built because there's no key at all. Fixed two ways: (1) `AnthropicLLMClient.__init__` now raises a clear `ValueError` immediately if constructed with no key — a missing key at deploy time is a configuration error, not a spend-cap condition, and conflating the two would violate the same "honest message, not a generic error" principle §4.4 states for the spend cap itself; (2) added `infrastructure/stub_llm.py`'s `StubLLMClient`, wired in by `presentation/api.py` only when `ANTHROPIC_API_KEY` is unset, so local/demo runs work with zero cost and zero crash — this was already the agreed approach for cost-sensitive local dev (avoid real paid LLM calls outside a deliberate, manual smoke test), just not yet wired into the actual FastAPI app before this bug surfaced it.
- **Newly identified gap, same shape as the spec's other accepted edge cases: no cross-match when only one source exposes a canonical URL for the same real-world story.** Tier 1 (URL) can't apply since only one side has a URL to match on; tier 3 (fuzzy) only runs "when no URL is available" (§4.3) — scoped to the article being processed lacking a URL, not to whether *some other* candidate article has one. Observed directly seeding milestone 1's static articles: a Finnhub article with a `canonical_url` and a Marketaux article without one, covering the same real story, landed as two separate `articles` rows with no path to match. Same category as §4.3's other accepted tier-3 limitations (fuzzy can't be a hard DB constraint) — not fixed in v1, but wasn't previously written down explicitly; noted here since it surfaced from running the real pipeline, not from re-reading the spec.
- **`PostgresArticleRepository.register_fuzzy_key` is a no-op** — the Postgres implementation derives the fuzzy match directly from `articles.published_at` + `articles.headline` at query time (`find_by_fuzzy_key`), so there's no separate fuzzy-key column/table to write to. The method still exists on the `ArticleRepository` protocol because it's meaningful for other implementations (e.g. an in-memory fake in tests) where fuzzy lookups aren't derived from already-stored columns.

A watchlist with 40 valid symbols and 1 typo should still get 40 correct `prices` rows, not zero.
- **`prices`'s primary key is `(symbol, date)` with an `ON CONFLICT ... DO UPDATE`, not append-only insert-only** — despite `decision_log.md` describing `prices` as "append-only, no rolling deletion," a same-day re-run of the batch job (a legitimate retry after a transient failure, or the job firing twice) must not error or create a duplicate row for the same trading day. "Append-only" here means no *deletion* path exists, not that a row is immutable once written on the same date; upserting a corrected close (e.g. Yahoo revising a still-forming bar) is the more correct interpretation and was verified live: inserting `TESTSYM` for one date, then upserting a revised close/volume for the same date, left exactly one row with the updated values.
- **`daily_symbol_features`'s date-grain `UNION` was verified live, not just written and assumed correct**: seeded a real article on a date with zero matching `prices` row (simulating weekend/holiday news), re-ran `dbt run`, and confirmed the resulting table gained exactly one new row for that date with a correct `article_count`/`avg_ingestion_lag_seconds` and null price columns — an inner join would have silently dropped it, which is exactly the failure mode `decision_log.md`'s union-grain entry already calls out as unacceptable. This was a genuine live check, not a restatement of the spec, since a typo (e.g. accidentally writing an inner join) would have passed every other test the same way it passed dbt's own not-null tests (which don't fail on a row being *missing*, only on a present row having a null required column).
- **dbt schema tests use a plain singular SQL test for `(symbol, date)` uniqueness (`tests/assert_no_duplicate_symbol_date.sql`) instead of `dbt_utils.unique_combination_of_columns`** — pulling in the `dbt_utils` package for one composite-uniqueness check adds a `packages.yml` + `dbt deps` step for a check expressible in four lines of plain SQL (`GROUP BY ... HAVING COUNT(*) > 1`); not worth the dependency for this project's scope.
- **Stats queries (`query-api/infrastructure/stats_queries.py`) were built in query-api, not daily-batch**, even though milestone 5's checklist item lists them alongside the batch job — they're a *read* path the stats UI will call at request time (milestone 6), and query-api already owns "the general authenticated user-facing API surface" (`project-structure.md`). Daily-batch's job is producing `daily_symbol_features`; consuming it for the UI is a separate concern with a separate lifecycle. No `/stats` HTTP endpoint was wired yet — deliberately deferred to milestone 6 alongside the Streamlit stats page itself, since an endpoint with no UI to call it would be untestable end-to-end anyway. This milestone's scope (per `milestone.md`'s own checklist wording, "complex-SQL stats queries") was the SQL existing and being verified correct, which was done: three real window-function queries (`AVG() OVER (ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)` for rolling volume, `PERCENTILE_CONT` for ingestion-lag p50/p95), all three verified live against real seeded Postgres data with hand-computed expected values (e.g. a 5-day rolling average checked against `(2+1+5+0+3)/5 = 2.2` by hand, not just "the query ran without error").
- **`daily_symbol_features` is created/dropped by the integration test itself in query-api, not assumed to already exist from a prior daily-batch run** — the table is normally produced by `services/daily-batch/dbt/models/daily_symbol_features.sql`, but query-api's test suite shouldn't depend on daily-batch having been run first as an out-of-band setup step invisible to anyone reading the test. The test's `CREATE TABLE IF NOT EXISTS` mirrors the dbt model's actual output columns exactly, so a schema drift between the two would need to be caught by actually running the real daily-batch job against the same database at some point — a known, accepted seam between the two services' test suites, same category as the existing query-api/processing shared-Postgres seam already logged above.

## Implementation (news backfill on watchlist add — new v1 feature)

- **User pushed back correctly on the initial design**: the first plan routed watchlist-add backfill through Pub/Sub (query-api publishes, processing consumes via /pubsub/push), mirroring the poller's real ingestion path. The user asked "if its direct request from user why it need to be in queue?" — a fair challenge. ## Bug found while investigating a flaky test (pgvector retrieval was never actually ranking by relevance)

- **`PgVectorRetriever.retrieve()`'s SQL had `ORDER BY e.article_id, e.chunk_index, e.vector <=> :query_vector`** — article_id sorts first, meaning retrieval was effectively ordered by (random) UUID, with vector similarity only breaking ties inside `SELECT DISTINCT ON (e.article_id, e.chunk_index)` groups. Since `(article_id, chunk_index)` is already `embeddings`' primary key, that `DISTINCT ON` was a no-op — every row is already unique on that pair — and existed only to satisfy `DISTINCT ON`'s requirement that `ORDER BY` start with the same columns. Net effect: `LIMIT top_k` returned whichever `top_k` rows happened to sort first by UUID, essentially at random, once there were more matching articles than `top_k`. This had been silently wrong since whenever this query was first written, undetected because dev/test databases rarely had enough concurrent embedded articles for a symbol to expose it.
- **How it surfaced**: re-running query-api's full test suite twice in a row (after two unrelated Docker Desktop crashes on this machine) showed the exact same test — `test_end_to_end.py::test_query_service_returns_grounded_answer_from_real_retrieval` — fail both times with the seeded, genuinely-relevant article missing from the top-5 results entirely, replaced by five unrelated real articles (Trump, an ETF, Buffett, an Apple price-target piece, Buffett-on-AI). A single flake would have been dismissible; the same specific test failing twice in a row on the same specific assertion was not, and read as a real signal instead of infrastructure noise (`docs/decision_log_claude.md`'s existing "processing/query-api integration tests share one live Postgres" seam was the first suspect, but didn't explain the *pattern* of the failure — a wrong ranking does).
- **Fix**: dropped the meaningless `DISTINCT ON`, changed `ORDER BY` to just `e.vector <=> :query_vector` (ascending cosine distance = most similar first). Added `tests/integration/test_pgvector_search.py` — a dedicated test for `PgVectorRetriever` that never existed before (it had only ever been exercised indirectly through `test_end_to_end.py`'s single-relevant-article fixture, which is exactly why an ordering bug like this could hide for so long). The new test seeds one genuinely relevant article plus 8 real-shaped decoys and asserts the relevant one ranks first and all returned scores are sorted descending — confirmed to fail against the old query (relevant article missing from top-3, scores unsorted) and pass against the fix.
- **Verified against real production data, not just the synthetic test**: with the live poller's actual 164 NVDA-tagged and 20 AAPL-tagged articles already in Postgres (many NVDA-tagged articles are only tangentially related — Marketaux's cross-symbol entity-matching tags articles beyond the queried symbol, a known behavior documented in milestone 3's notes), asking "What is happening with Nvidia AI hardware and US-China trade talks?" against the fixed retriever correctly ranked "3 AI Hardware Stocks Linked To Nvidia And US China Trade Talks" first (score 0.7713, a clear margin over the next result at 0.5322) — the article that actually matches the question, out of 164 real candidates.
- **A second, unrelated flaky test surfaced by the exact same live-poller pollution mechanism**: `test_overview_stats_scoped_to_watched_symbols` seeded two "today" articles under the real ticker `AAPL` and asserted `articles_ingested_today == 2` — correct only when nothing else touches `AAPL` that same calendar day. The live poller had genuinely ingested 20 real AAPL articles that day, so the real count was 22, not 2. Fixed by seeding under made-up symbols (`TESTSYM`/`TESTSYM2`) instead of a real, actively-polled ticker — the same pattern already used correctly elsewhere in this project (`test_prices_repo.py`, `test_pgvector_search.py`'s new decoys). A live-poller-connected test suite genuinely cannot assert exact counts against real ticker symbols; this is now the second confirmed instance of that exact failure mode, worth treating as a standing rule for any future test in this codebase, not a one-off.

## Real bug reported directly by the user, from actually clicking the feature in production

The actual application code had been correct since the compose-file mount was added; a plain `docker compose down query-api && docker compose up -d query-api` restored the correct name and the real HTTP-triggered path then worked immediately. ## Correction: the 7d/30d toggle should be per-symbol, not page-wide (user caught this immediately)

- **User's correction landed the moment the single-toggle version shipped**: "7d 30d should be per symbol." The page-wide `?days=` design above meant NVDA and AAPL couldn't be viewed at different windows simultaneously — a real usability gap the design discussion beforehand hadn't surfaced, since nothing in the earlier back-and-forth (which was mostly about *what* replaces the ingestion-lag block, not *how the toggle scopes*) had actually asked whether one page-wide window made sense once every symbol has its own independent history.
- **Fetch-strategy question surfaced immediately once per-symbol was the target**: a per-symbol toggle needs per-symbol data on hand to switch instantly, which conflicts with the existing single `?days=` query param design (one window for the whole request). Presented two options directly: keep `?days=` and refetch per symbol on toggle (more round trips, unchanged response shape) vs. drop `?days=` and always return both windows for every symbol in one response (bigger single response, zero round trips on toggle, an instant client-side redraw). User chose the latter.
- **The user immediately followed up with the real scaling question this choice raises**: "but what if we have 100 symbols wont that too big?" — a fair, specific concern that needed a specific answer, not reassurance. Worked through it directly: the JSON payload itself stays trivially small even at 100 symbols (a few dozen small rows per symbol per window, tens of KB total, nowhere near a real HTTP response size concern) — the actual cost that scales with symbol count is database queries, since the original single-window design already ran 3 queries per symbol (`total_ingestion`, `rolling_article_volume`, `price_deltas`), and naively doubling for two windows would mean 6 queries × N symbols per page load.
- **Resolved by fetching the 30-day window once per symbol and computing 7-day figures from the same data, in SQL, not in two separate round trips**: `rolling_article_volume` now computes `rolling_avg_7d` (`ROWS BETWEEN 6 PRECEDING`) and `rolling_avg_30d` (`ROWS BETWEEN 29 PRECEDING`) as two window functions over one 30-day-filtered `SELECT`, not two queries with two different `WHERE` clauses. `total_ingestion` returns `(total_7d, total_30d)` as a tuple from one query, using `SUM(article_count) FILTER (WHERE date >= CURRENT_DATE - INTERVAL '7 days')` alongside a plain `SUM(article_count)` for the 30-day total — a single conditional aggregate rather than a second full query. `price_deltas` simply returns the full 30-day list once; day-over-day `price_change_pct` doesn't change based on window size, so the 7d view is just the API layer slicing the last-7-days tail of the same list in Python, no extra query needed. Net result: 3 queries per symbol regardless of how many windows the response exposes — the user's scaling concern from `?days=` doubling to 6 queries never actually materializes.
- **`GET /stats` dropped `?days=` and the accompanying `Literal`/`Query` validation entirely** — with both windows always returned, there's no query param left to validate; the earlier `Literal[7,30]`-vs-plain-`int` bug (`decision_log_claude.md`, two entries up) is now moot rather than fixed-in-place, since the code path that triggered it no longer exists.
- **New nested response shape**: `SymbolStatsResponse` now holds `window_7d`/`window_30d`, each a `WindowStatsResponse` (`total_articles`, `rolling_volume`, `price_deltas`) — replacing the old flat per-symbol shape that mixed a single window's figures directly into the symbol object. `RollingVolumePoint`'s domain dataclass gained `rolling_avg_7d`/`rolling_avg_30d` (replacing the single `rolling_avg` field from the first version), computed once per point and reused for both response windows rather than recomputed.
- **A test bug in my own first attempt at the "windows genuinely differ" integration test, caught by actually running it rather than trusting the assertion**: seeded a lone row 10 days back with nothing in between, expecting the 7-row rolling window to exclude it — but `ROWS BETWEEN N PRECEDING` counts *rows*, not calendar days, and with a real date gap (no rows for days 5-9), that lone day-10 row genuinely was among the "6 preceding rows" from the dataset's perspective, making the 7-day rolling average pick it up too. This exposed a modeling assumption already implicit in the original committed code (row-count windows, not date-range windows) that happens to be correct in production only because `daily_symbol_features`'s date grain has no gaps under normal operation (every day gets a row via the prices/article-activity union, `decision_log.md`) — but is a footgun for any test that seeds sparse, gapped data without realizing it. Fixed the test by filling in the gap days with zero-article rows before adding the day-10 outlier, matching what real gapless data actually looks like, rather than changing the SQL (which is correct for its actual input shape).
- **Live-verified the corrected per-symbol, single-fetch design against the real running stack**: `GET /stats` now returns `window_7d`/`window_30d` for every watched symbol (AAPL/NVDA/AMD/GOOG/NFLX) in one call with no query param, confirmed via a live `curl` against the real user's account after repopulating `daily_symbol_features` with a real `docker compose --profile batch run --rm daily-batch` sweep. All three test suites re-run clean: query-api 103 passed (up from 100 — new tests for the dual-window queries and the per-symbol response shape), UI 11 passed, daily-batch 20 passed, unaffected by this change.

## News backfill widened to 30 days to match price backfill — surfaced a real Finnhub reliability problem

- **User's follow-up question directly drove this**: "and when first add symbol it pull last 30d news right?" — the honest answer at the time was no, news backfill (`BackfillService.BACKFILL_WINDOW_DAYS`) was still 14 days even though the price/feature-store side had already moved to 30 (an earlier change in this same session). Widened `BACKFILL_WINDOW_DAYS` to 30, which affects both the initial on-add pull and each `load_more()` extension step (one shared constant, per the user's explicit choice over adding a second constant just for the initial pull).
- **All test call-shape assertions in `test_backfill_service.py` needed updating, not just the constant** — `FakeNewsClient`'s calls are keyed by exact `(from_date, to_date)` tuples, so widening the window changed every expected call in the file. Rewrote the whole test file rather than patch numbers in place, computing the real chunk boundaries via the actual chunking arithmetic (see below) instead of hand-deriving them, to avoid the exact kind of off-by-one mistake that bit the Stats page's rolling-window test earlier in this session.
- **Live-testing the widened window immediately surfaced a real, reproducible Finnhub problem, not a hypothetical one**: adding INTC (a real, moderately active symbol) produced a genuine `httpx.ReadTimeout` even at a 60s client timeout. Isolated the cause directly rather than guessing: a raw `httpx.get` from inside query-api's own container to Finnhub's `company-news` endpoint for INTC returned in **9.3s at a 14-day range** but **timed out entirely (47-98s, never succeeding) at 20, 25, and 30-day ranges** — a real, measured threshold, not a fluke, confirmed by testing multiple widths in sequence.
- **Fixed with chunked fetching, `FETCH_CHUNK_DAYS = 14`** — `_run_backfill` now loops backward from `to_date` in <=14-day slices (`while chunk_to > from_date: chunk_from = max(from_date, chunk_to - timedelta(days=14))`), calling Finnhub once per slice and summing results, rather than one call for the full requested range. For a 30-day window this produces 3 chunks: `[today-14, today]`, `[today-28, today-14]`, `[today-30, today-28]` — verified by actually running the chunking arithmetic in a throwaway script before writing the test's expected values, not by hand computation (hand computation is exactly what produced the earlier Stats-page rolling-window test bug in this same session).
- **A second, harder problem found only after chunking was actually live-tested, not assumed fixed by chunking alone**: re-added INTC with the chunked fix in place — still failed, still a `ReadTimeout`, now inside `response.read()` (mid-stream, not just connection setup). Isolated further: the *same* 14-day INTC request that had returned in 9.3s in the first isolation test returned in 2.1s on a later retest, then **every one of 4 immediately-following sequential requests to the identical endpoint timed out past 30s**. This ruled out "chunk width" as the actual variable — a request that already succeeds once at 14 days does not reliably succeed again moments later. The real behavior is Finnhub's endpoint being intrinsically unreliable/rate-limited under repeated calls from this key, not a stable size threshold chunking could route around.
- **Presented the finding and three options directly rather than picking one unilaterally**: keep news at 14 days (revert), keep pushing on 30 days with longer timeouts and retries, or make each chunk best-effort so a slow/failed chunk doesn't fail the whole request. User chose best-effort — the correct choice given the measured behavior: retries would just re-encounter the same unreliable endpoint, and reverting would abandon the very feature just requested over a third-party API's flakiness rather than designing around it.
- **Implemented as a per-chunk `try`/`except (httpx.TimeoutException, httpx.HTTPStatusError)`** inside the existing chunk loop — a failed chunk logs `backfill_service.chunk_failed` (symbol, date range, error) and the loop continues to the next chunk rather than propagating. **First version of this fix unconditionally called `set_earliest_backfilled` regardless of how many chunks succeeded** (reasoned at the time: recording a partial/inconsistent range would make a later "load more" click's arithmetic ambiguous) — this reasoning turned out to be wrong in the case that actually matters, and was corrected the same session once it produced a real reported bug (see below): a symbol whose *every* chunk fails still needs to end up "not backfilled," not "backfilled with zero articles," or there is no path back to retrying it.
- **Live-verified against the real running stack while Finnhub was still in its actually-degraded state, not a synthetic failure injected for the test**: added INTC for real after the fix — logs showed `backfill_service.chunk_failed` for 2 of the 3 chunks (`[2026-09-07,2026-09-21]` and `[2026-08-24,2026-09-07]`, both real timeouts), the request still completed with a real `201` in ~2 minutes (slow, because it still had to wait out two real timeouts before giving up on each, but *not fatal*), and Postgres confirmed 17 real INTC articles landed (from the one chunk that succeeded) plus real `prices` rows from the independent, unaffected Yahoo-based price-backfill trigger running in parallel. This is the concrete proof the fix addresses the actual failure mode: the symbol gets added and whatever news is reachable comes through, instead of the whole request 500ing because a third-party API had a bad few minutes.
- All 105 query-api tests pass (up from 103 — two new tests for the best-effort chunk behavior: one confirming a failed chunk doesn't raise and other chunks still run, one confirming progress recording — later corrected, see below).

## Watchlist-add and load-older moved off the request path onto Celery + RabbitMQ (user request)

- **User's framing was direct and specific**: "when add symbol shouldnt it be instant, add leave loading news as background job?" — correctly identifying that the synchronous backfill (still blocking `POST /watchlist`'s response even after the best-effort chunk fix above) was the wrong place for this latency to live at all, not just something to make more resilient to individual failures.
- **User explicitly asked for something Hangfire-shaped** — a durable, persistent job system, not FastAPI's built-in `BackgroundTasks` (in-process only, no persistence, lost on a crash/restart). Confirmed this distinction mattered to the user before building anything, rather than defaulting to the simpler option.
- **Python's Hangfire-equivalent is Celery, which needs a message broker — chose RabbitMQ over Celery's other common option (Redis) after being asked directly ("rabbit ? cant it be a container in cloudrun?")**: walked through why "RabbitMQ as a container on Cloud Run" doesn't actually solve the durability problem Cloud Run's storage model has no real answer for — an "ephemeral disk" is still tied to instance lifetime despite the name, and a GCS-bucket-as-filesystem mount doesn't give RabbitMQ genuine block-device semantics (fsync, file locking) a broker's durability actually depends on. Real persistent disks are a GKE/Compute Engine feature, not Cloud Run's.
- **Also verified rather than assumed there's no free-tier answer**: initially stated (without checking) that no free managed RabbitMQ exists — the user pushed back ("actaully there is free rabbitmq no? free tier exist?"), which was the right challenge: a live search confirmed CloudAMQP's "Little Lemur" shared plan is a genuine, usable free tier (1M messages/month, 20 connections, 100 queues), available directly through GCP Marketplace. Settled on RabbitMQ (local: plain `docker-compose` container; cloud: CloudAMQP free tier, deferred to milestone 7) + a Celery worker (local: separate `celery-worker` compose service; cloud: a Cloud Run Service with `min-instances=1`, since a worker also needs to stay connected to consume).
- **`WatchlistService`'s two separate optional dependencies (`BackfillTrigger`, `JobTrigger`) collapsed into one `BackfillQueue` Protocol** (`enqueue_symbol_backfill`) — both news backfill and the price/feature-store job trigger now happen inside a single Celery task (`backfill_symbol`), so the application layer only needs one enqueue call, not two separate trigger calls. `CeleryBackfillQueue` implements it by publishing to the task by name (`celery_app.send_task("backfill_symbol", ...)`) rather than importing `celery_app`'s own task functions directly — keeps the FastAPI request path from pulling in the worker's DB/HTTP client wiring.
- **New `infrastructure/backfill_dependencies.py` factory, shared by `api.py` and `celery_app.py`** — extracted the `BackfillService`/`JobTrigger` construction (engine, httpx clients, `FinnhubNewsClient`, `ProcessingIngestClient`, `PostgresBackfillProgressRepo`, `SystemClock`, `LocalDockerJobTrigger`) that used to live only in `api.py`'s module scope, since the Celery worker process needed the exact same wiring and duplicating it inline would risk the two processes drifting apart over time.
- **Real, non-obvious infrastructure bug hit immediately on first boot, found live not by reading docs first**: `celery-worker` crash-looped with `amqp.exceptions.InternalError: Queue.declare: ... Feature transient_nonexcl_queues is deprecated`. Root cause: RabbitMQ 4.x has deprecated the transient+non-exclusive queue pattern Celery/kombu's internal machinery declares by default, and rejects it outright rather than degrading gracefully. This mattered for the *cloud* choice too, not just local dev — verified live that CloudAMQP's shared plans already run RabbitMQ 4.x (their own changelog references 4.2), so pinning local RabbitMQ to an older version (3.13) would only defer this exact failure to the real cloud migration, not fix it. Fixed client-side instead, which works identically regardless of broker version or hosting: declared the task queue as `durable=True` (RabbitMQ's own documented recommended alternative to the deprecated pattern).
- **A second layer of the same bug, found only after the first fix was live-tested, not assumed sufficient**: even with the task queue durable, the worker still crashed at boot with the identical error — traced via full traceback to `kombu/pidbox.py`'s `reply_queue`, used by Celery's `mingle`/`gossip` startup bootsteps to broadcast worker state, which declares its *own* transient queue regardless of `worker_enable_remote_control`/`worker_send_task_events` settings (tried both, confirmed live neither stops this). The actual fix (`--without-mingle --without-gossip --without-heartbeat`) is CLI-flag-only, not available as a settings-file config key (a known, longstanding Celery limitation, celery#2566) — added to the worker's `command:` in `docker-compose.yml`. Not a loss of real functionality here: mingle/gossip only matter for multi-worker coordination, and this is a single-worker setup.

## Real bug reported live: TSLA's day-over-day price-change chart stopped dead at the last Friday, silently dropping every day after a weekend

- **User's exact question**: "why Day-over-day price change ends at 2026-09-18 tsla" — 09-18 was a Friday; 09-19/09-20 (Sat/Sun) have no `prices` row (markets closed, expected), but 09-21 (Monday) does have a real price and should have shown a real day-over-day change too.
- **Root cause**: `daily_symbol_features`'s `price_change_pct` used a plain `LAG(price_close) OVER (ORDER BY date)` — Postgres has no `IGNORE NULLS` on window functions, so `LAG` returns the literally-previous *row*, not the previous row *with a real value*. Since `date_grain` is a union of `prices` dates and article-activity dates (news keeps arriving on weekends even though prices don't), Saturday/Sunday exist as real rows with `price_close = NULL` sitting between Friday and Monday. Monday's `LAG` therefore looked at Sunday's null, not Friday's real close, and the `case` guard (`lag(price_close) is not null`) correctly-per-its-own-logic returned null — silently dropping every trading day that immediately follows a null-price gap, not just weekends but any holiday too.
- **This was a real logic bug, not the deliberate behavior the model's own comment described** — the comment said "gated on both days actually having a price, no fabricated deltas across a gap," which was written to stop a delta being computed against a missing/zero price, not to suppress a perfectly real comparison across an expected weekend gap.
- **Fix**: rewrote the model with a manual "carry the last real price forward" pattern — `count(price_close) OVER (PARTITION BY symbol ORDER BY date)` increments a group id each time a real price appears (nulls don't increment it), then `MAX(price_close) OVER (PARTITION BY symbol, price_group ORDER BY date)` fills every null-price row in that group with the one real price it follows. `price_change_pct` now compares `LAG()` of that carried-forward value, not the raw possibly-null `price_close` — so Monday correctly compares against Friday's close across the weekend gap, while a symbol with no earlier trading day at all still correctly gets `null` (no fabricated delta).
- **Deployment gap caught mid-fix**: `daily-batch`'s `docker-compose.yml` entry bakes its dbt project into the image at build time (`build: ./services/daily-batch`, no source volume mount) — editing the `.sql` file on disk and re-running `docker compose run --rm daily-batch` silently kept using the *old* compiled model until `docker compose build daily-batch` actually ran. First verification attempt showed no change at all because of this; confirmed by checking `target/compiled/.../daily_symbol_features.sql` still lacked the new CTEs.
- **New dbt test, verified against both correct and buggy code, not just written and trusted**: `assert_price_change_pct_skips_null_price_gaps.sql` fails if any row has a real `price_close`, an earlier real price exists for that symbol, but `price_change_pct` is still null (a possible comparison that wasn't made). Confirmed it actually fails against a temporarily-reverted buggy version of the model (4 real failures) before confirming it passes against the fix — not just trusting the test's logic on paper.
- **Live-verified against real TSLA data**: 09-21's `price_change_pct` went from `None` to `2.69%` (computed against Friday 09-18's close, correctly skipping the Sat/Sun gap) after rebuilding the `daily-batch` image and re-running the full watchlist sweep.

## Real bug reported live: an unhandled Anthropic BadRequestError killed a streaming /query response, surfacing to the UI as an opaque connection error

- **User's exact report**: `httpx.RemoteProtocolError: peer closed connection without sending complete message body` from Streamlit's `st.write_stream` on the query panel. The real cause, found in `query-api`'s logs, was several layers downstream of what the UI ever saw: `anthropic.BadRequestError: ... This API key is not scoped to a workspace, so this request must include the anthropic-workspace-id header ...` — a genuine account/key configuration issue, not a code bug in the request itself.
- **Why it looked like a raw connection failure instead of a real error**: `AnthropicLLMClient.stream()` is a generator FastAPI wraps in a `StreamingResponse` — once streaming starts, an unhandled exception inside the generator has nowhere to go but to blow up the response mid-flight, which the ASGI layer surfaces as simply closing the TCP connection. The client-side `httpx.RemoteProtocolError` is real but tells the user nothing about what actually happened; the existing `except PermissionDeniedError`/`except RateLimitError` handlers (added for the spend-cap UX) only covered two specific error types, and `BadRequestError` fell through both, uncaught.
- **Two separate, unrelated fixes landed together**: (1) `llm_model` had a stale date-suffixed model ID (`claude-haiku-4-5-20251001`) — current model IDs never carry a date suffix; corrected to `claude-haiku-4-5` in both `settings.py`'s default and `AnthropicLLMClient`'s own fallback default. (2) Added `except anthropic.BadRequestError: yield CONFIG_ERROR_MESSAGE` alongside the existing spend-cap handlers — a `BadRequestError` is a setup/config problem, not a spend-cap condition, so it gets its own distinct, honest message rather than silently being reported as "spending cap reached" (which would have been actively misleading about the real cause). The underlying workspace-scoping issue itself is an Anthropic-account/key configuration matter outside this codebase — not something fixable in application code, only mitigated so it fails gracefully instead of crashing the stream.
- **TDD**: new `test_bad_request_error_yields_a_config_error_message_instead_of_raising` constructs a real `anthropic.BadRequestError` (via `httpx2.Response`/`Request`, since this SDK version is built on `httpx2` not `httpx` — confirmed by inspecting the exception's actual constructor signature rather than guessing) and asserts `stream()` yields the config-error message instead of raising.

- **New pieces**: `application/aggregate_question_detection.py`'s `is_busiest_symbol_question()` — a plain regex (`\b(most|least|fewest|highest|lowest)\b.*\b(news|article|articles)\b`), not a second LLM call. `StatsQueries.busiest_symbol_day(symbols)` — queries `articles`/`article_symbols` directly (real-time), not `daily_symbol_features`, for the same reason `overview_stats` already does: the dbt-managed table is only as fresh as the last daily-batch run and can go missing entirely after a Postgres restart with nothing to rebuild it (confirmed live again this session — the table was gone when this feature was being tested, from the earlier Docker Desktop wipe never getting a fresh sweep). `QueryService.answer()` checks the pattern first; when it matches, it skips vector retrieval entirely, calls the real aggregate query, and hands the LLM the already-computed fact to phrase naturally — explicitly instructed not to alter the numbers/dates it's given, the same "ground everything, never let the model fill gaps with a guess" discipline as the rest of this prompt.
- **`AggregateQueries` is an optional constructor param on `QueryService`** (`| None = None`), matching this codebase's established pattern for every other optional collaborator (`BackfillQueue`, `JobTrigger`, `RebuildDebounceService`, ...) — existing callers/tests that don't wire it in keep working exactly as before, falling back to ordinary retrieval even for a matching question if no aggregate-queries collaborator is configured.
